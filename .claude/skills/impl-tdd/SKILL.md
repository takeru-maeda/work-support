# 工程 2: TDD による実装

**入口条件**: 改修の記録が `status: approved`（または再開時の `in_progress`）で、チェックリストの「★ 承認」に印があること。無ければ実装に入らず、autonomous-impl の承認ゲートに戻る。

## 手順

1. 改修の記録の `status` を `in_progress` にする。
2. **既存コードを変えるときは、触る前に今の挙動をテストで固定する**（特性化テスト）。挙動を変えないつもりの箇所が、変わっていないことの保証になる。
3. 受け入れ基準ごとに **Red → Green → 小さな Refactor** を回す。
   - **Red**: 失敗するテストを先に書き、実行して失敗することを確かめる。テストの名前に `AC-<feature>-NN` を入れる
   - **Green**: 通すための最小限の実装を書く
   - **小さな Refactor**: 緑のまま、重複の除去や命名の改善だけをする（大きな整理は工程 5）
4. 書き方は、改修の記録の「手本にする既存コード」と、パッケージの `CLAUDE.md`、`.claude/rules/` に従う。コメントは「なぜ」を書き、コードの言い換えは書かない。公開する関数には JSDoc を書く。
5. 型チェックはこまめに回す（コマンドはパッケージの `CLAUDE.md`「ビルド・テスト・型チェックの鉄則」）。
6. api で DB に触れるテストは、ローカルの Supabase で回す結合テスト（`*.int.test.ts`）に書く（手順は `packages/api/CLAUDE.md`「ビルド・テスト・型チェックの鉄則」）。業務ロジックの細かい分岐は、repository を差し替えた service の単体テストで確かめる。
7. 実装の途中で、承認された計画から外れる必要が出てきたら:
   - 小さな調整（ファイルの分け方など）は進めてよい。改修の記録に「計画からの変更」として書き残す
   - 仕様（受け入れ基準）や影響範囲が変わるときは、手を止めて人間に確かめる

## 出口条件

- すべての受け入れ基準に、通っているテストがある（自動テストにできないものは、工程 4 で確かめる方法を記録に書く）
- 型チェックが通っている
- チェックリストの「2」に印を付け、**`impl-bug-check`（工程 3）** を読み込む
