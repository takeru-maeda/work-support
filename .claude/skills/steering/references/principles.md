# steering の原則

steering は**プロジェクトの記憶**であって、網羅的な仕様書ではない。機能の詳しい振る舞いは `docs/specs/<feature>/spec.md` に書く。

## 粒度

### 黄金律
> 「新しいコードが既存のパターンに沿っているなら、steering は更新しなくてよい」

### 書くもの
- 構成のパターン（機能単位、層構造）
- 命名の規約
- import の方針
- 設計上の判断（状態管理、認証方式など）とその理由
- 技術の基準（主要なフレームワーク、守る水準）

### 書かないもの
- ファイルの一覧
- コンポーネントひとつひとつの説明
- 依存パッケージの全一覧
- 実装の細部（コードを正とする）
- エージェント用のツール（`.claude/` など）の使い方の説明（「`.claude/settings.json` で禁止している」のような、強制している仕組みへの短い参照は可）

### 例

**悪い例**（仕様書のような書き方）:
```markdown
- /components/Button.tsx - 種類を持つ主ボタン
- /components/Input.tsx - 検証つきの入力欄
- /components/Modal.tsx - モーダル
...（50 ファイル以上）
```

**よい例**（プロジェクトの記憶としての書き方）:
```markdown
## UI コンポーネント（`/components/ui/`）
デザインシステムにそろえた再利用部品
- 役割で名前を付ける（Button、Input、Modal）
- コンポーネントと型をあわせて export する
- 業務ロジックを持たない
```

## セキュリティ

次のものは書かない: API キー、パスワード、認証情報、DB の URL、内部の IP、そのほかの秘密情報。

## 品質の基準

- **1 ファイル 1 テーマ**
- **具体例を添える**: パターンはコードで示す
- **理由を書く**: なぜその判断をしたのか
- **読み切れる長さ**: 100〜200 行が目安。**200 行を超えたら削る・分けることを考える**。中核の 3 ファイル（product / tech / structure）は毎回読み込まれるので、3 つ合わせて 300 行以内（`scripts/harness-check.mjs` で確かめる）
- **日本語で書く**（コードと識別子はそのまま）

## 更新するとき

- 人間が書いた節や例は残す
- 追記を基本とする（置き換えるのは、コードと食い違って誤りになった記述だけ）。ただし、誤りになった記述は残さず書き換える
- 1 つの機能だけの振る舞いや設計は、steering ではなく、その機能の `docs/specs/<feature>/spec.md` に書く
- 何をなぜ変えたか（と更新後の行数）を報告に書く

## 補足

- テンプレートは出発点。プロジェクトに合わせて変えてよい
- 追加の steering も、中核と同じ粒度の原則に従う
- steering のファイルは、すべてプロジェクトの記憶として読み込まれる
- 追加の steering も、中核と同じだけ大事に扱う

## ファイルごとの焦点

- **product.md**: 目的、価値、使われ方（機能の網羅ではない）
- **tech.md**: 主要な技術、基準、規約（依存の全一覧ではない）
- **structure.md**: 構成のパターン、命名の規約（ディレクトリツリーではない）
- **それ以外**: 特定の分野のパターン（API、テスト、セキュリティ、UI など）
