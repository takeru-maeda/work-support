# steering の管理

<background_information>
**役割**: `docs/steering/` を、プロジェクトの記憶として保つ。

**使命**:
- 初回作成: コードベースから中核の steering を作る
- 同期: steering とコードベースのずれをなくす（保守）
- 保全: 人間が書いた内容は尊重する。更新は追記を基本とする

**成功の条件**:
- steering に書かれているのは**パターンと原則であって、網羅的な一覧ではない**
- コードとのずれが検出され、報告されている
- `docs/steering/*.md` はすべて同じ重みで扱う（中核も追加分も）
- **各ファイルが 100〜200 行に収まっている**。中核の 3 ファイル（product / tech / structure）は毎回の会話で読み込まれるため、3 つ合わせて 300 行以内に保つ（`scripts/harness-check.mjs` で確かめる）
</background_information>

**最初に [references/principles.md](references/principles.md) を読む。** 書く粒度、書かないもの、更新のしかたはそこにある。

<instructions>

## 状況の判定

| 状況 | モード |
| --- | --- |
| `docs/steering/` が空、または中核のファイル（product.md / tech.md / structure.md）が無い | **初回作成** |
| 「steering を同期して」「steering を更新して」、定期的な掃除 | **同期** |
| `impl-docs`（autonomous-impl の工程 7）から、改修の記録と変更ファイルを渡された | **差分モード** |
| 「〇〇の steering を作って」、新しい分野の規約をまとめたい | **追加** |

---

## 初回作成

1. [references/templates/core/](references/templates/core/) のテンプレートを読む
2. コードベースを必要なときに必要な分だけ調べる（Glob でファイルを探し、Read で README や package.json を読み、Grep でパターンを探す）
3. 一覧ではなくパターンを抜き出す
   - product: 目的、価値、主な機能
   - tech: フレームワーク、判断、規約
   - structure: 構成、命名、import
4. テンプレートに沿って steering のファイルを書く
5. [references/principles.md](references/principles.md) に照らして見直す
6. 要約を示してレビューを頼む

**焦点**: 判断の手がかりになるパターン。ファイルや依存の一覧ではない。

---

## 同期

1. 既存の steering（`docs/steering/*.md`）をすべて読む
2. コードベースの変化を、必要な分だけ調べる（広く読むときは Explore に任せ、結論だけを受け取る）
3. ずれを見つける
   - **steering → コード**: steering にあるのにコードに無い・違う → 警告
   - **コード → steering**: コードに新しいパターンがある → 更新の候補
   - **追加の steering**: 今も役に立っているかを確かめる
4. 更新する（追記を基本とし、人間が書いた内容は残す）。**ただし、追記の前に、コードと食い違って誤りになった記述や、パターンではなく一覧・実装の細部になっている記述を探し、それは削る・まとめる**。同期のあとでファイルが 200 行を超えるなら、どこを削るかを提案する
5. 報告する（更新したこと、警告、提案）

**更新の考え方**: 置き換えより追記。人間が書いた節は残す。

---

## 差分モード（改修のたびの呼び出し）

改修のたびに呼ばれるため、**放っておくと少しずつ追記が積み重なって steering が膨らむ**。次の手順で、更新を最小限に抑える。

1. **入力**: 改修の記録（`docs/specs/<feature>/changes/v<X.Y.Z>-<slug>.md`）と、変更したファイルの一覧（`git status --porcelain`）
2. **まず黄金律で判定する**: 「新しいコードが既存のパターンに沿っているなら、steering は更新しない」。更新が必要なのは、次のどれかに当たるときだけ
   - 新しい**パターンや規約**を持ち込んだ（新しい層、新しい共通部品の置き場、新しいエラーの返し方など）。**1 つの機能だけの振る舞いや設計は、steering ではなく、その機能の `spec.md` に書く**
   - **技術の変更**（ライブラリの追加・置き換え、主要なバージョンの更新）
   - steering の記述が、今回の変更で**誤りになった**
   どれにも当たらなければ「不要（理由）」を返して終える。**多くの改修はこれに当たる**
3. **更新する**: 影響するファイルの該当箇所だけを直す
   - 誤りになった記述は、書き足すのではなく**書き換える**
   - 新しいパターンは、既存の節の中に**数行で**加える（コードの例は、パターンを示すのに必要な最小限）
   - 新しいファイルは作らない（必要なら「追加」を提案する）
4. **報告する**: 呼び出し元に「更新した（ファイル名、変えた行の要点、更新後の行数）」か「不要（理由）」を返す

## 追加（旧 /kiro:steering-custom）

1. 分野と、書きたいパターンをユーザーに確かめる（はっきりしていれば聞かなくてよい）
2. [references/templates/custom/](references/templates/custom/) に同じ分野のテンプレートがあれば、出発点に使う（api-standards / testing / security / database / error-handling / authentication / deployment）
3. 関係するコードを、必要な分だけ調べる（Glob / Read / Grep）
4. 書く
   - テンプレートの構成に沿う
   - [references/principles.md](references/principles.md) に従う
   - 一覧ではなくパターンに絞る
   - **100〜200 行**（2〜3 分で読める長さ）
   - 既存の steering と内容を重複させない
5. `docs/steering/<分野>.md` に置く。その分野のファイルを編集するときに読み込まれる `.claude/rules/*.md` から参照を張ることを提案する

## 粒度の原則

[references/principles.md](references/principles.md) より:

> 「新しいコードが既存のパターンに沿っているなら、steering は更新しなくてよい」

一覧ではなく、パターンと原則を書く。

**悪い例**: ディレクトリツリーのファイルをすべて並べる
**よい例**: 構成のパターンを、例を添えて説明する

</instructions>

## ツールの使い方

- Glob: ソースや設定のファイルを探す
- Read: steering、ドキュメント、設定を読む
- Grep: パターンを探す

**必要になったときに取りに行く**: 最初にまとめて読み込まない。

## 出力

ファイルは直接更新し、会話には要約だけを書く。

### 初回作成
```
## steering を作成しました
- product.md: <短い説明>
- tech.md: <主な技術>
- structure.md: <構成>

内容をレビューして、正として承認してください。
```

### 同期
```
## steering を更新しました
- tech.md: React 19.1 → 19.2
- structure.md: API 呼び出しの置き場のパターンを追記（106 → 109 行）

## コードとのずれ
- `features/foo` が import の順序の規約に沿っていない

## 提案
- `<分野>.md` の追加を検討
- structure.md の「移行途中の点」は P7 で解消済みなので削除を検討
```

### 差分モード
```
steering: 不要（既存の service / repository のパターンに沿った変更のため）
```
または
```
steering: 更新した — error-handling.md「エラーの出どころ」に UI からの再送の扱いを 2 行追記（51 → 53 行）
```

## 例

### 初回作成
**入力**: steering が空の React / TypeScript のプロジェクト
**出力**: パターンを書いた 3 ファイル（「機能単位の構成」「TypeScript strict」「React 19」）

### 同期
**入力**: 既存の steering と、新しく増えた API のディレクトリ
**出力**: structure.md を更新し、パターンに沿っていないファイルを警告し、api-standards.md の追加を提案

### 差分モード
**入力**: 目標の一覧に絞り込みを足した改修（既存のパターンどおり）
**出力**: 「steering: 不要」

## 安全と迷ったとき

- **セキュリティ**: キー、パスワード、秘密情報を書かない（原則を参照）
- **迷ったとき**: どちらの状態が正しいか判断できなければ、**両方の状態を報告に書いてユーザーに聞く**（ファイルに両方を書かない）
- **保全**: 迷ったら、置き換えるより追記する。ただし誤りになった記述は残さない

## 補足

- `docs/steering/*.md` はすべてプロジェクトの記憶として読み込まれる（中核の 3 つは毎回、ほかは必要なときに）
- テンプレートと原則は、このスキルの `references/` にあり、調整してよい
- 一覧ではなくパターンを書く
- 黄金律: パターンに沿った新しいコードは、steering の更新を必要としない
- エージェント用のツールの置き場（`.claude/` など）の使い方は書かない（「`.claude/settings.json` で禁止している」のような、強制している仕組みへの短い参照は可）
- 1 つの機能の振る舞いや設計は steering ではなく `docs/specs/<feature>/spec.md` に書く
