# 自律実装フロー（司令塔）

ゴールは「動くコード」ではなく、**人間がほぼ指摘なしでレビューし、そのままコミットできる状態**。このスキルは工程の**順番・ゲート・原則**だけを持つ。各工程の手順は工程スキル（`impl-*`）にあり、**その工程に入るときに必ず Skill ツールで読み込んでから実施する**（記憶で済ませない）。

## 原則

- **親エージェントが連続したコンテキストで最後までやる。** 設計・実装・検証・リファクタ・ドキュメント更新を別のエージェントに分けない。後の工程ほど前の工程の文脈（設計の判断、危ない箇所の勘所）に頼るため、分けると文脈が落ちて既存の機能を壊す。
- **独立した目が必要な工程だけ、読み取り専用のサブエージェントに任せる**: 広い探索（`Explore`）、仕様レビュー（`spec-reviewer`）、バグ点検（`bug-reviewer`）、最終レビュー（`/code-review`）。作る人と判定する人を分ける。
- **既存の近いコードのパターンに合わせる。** 独自のやり方を持ち込まない。
- **工程を飛ばさない。** 重さは規模で調整してよい（下の表）。
- **工程スキルは同じコンテキストの中で読み込む。** 工程の切り替えは、改修の記録（`docs/specs/<feature>/changes/v<X.Y.Z>-<slug>.md`）の「工程チェックリスト」に印を付けて行う。

## 工程

| # | 工程 | 読み込むスキル | 担当 |
| --- | --- | --- | --- |
| 0 | 仕様の把握 | `impl-investigate` | 親（広い探索は Explore） |
| 1 | 改修の記録の作成（M 以上は仕様レビューも） | `impl-spec` | 親 + `spec-reviewer` |
| ★ | **承認ゲート**: 改修の記録を提示して止まる | — | 人間 |
| 2 | TDD による実装 | `impl-tdd` | 親 |
| 3 | バグの自己点検 | `impl-bug-check` | 親 + `bug-reviewer` |
| 4 | 動作検証 | `impl-verify` | 親 |
| 5 | リファクタリング | `impl-refactor` | 親 |
| 6 | コードレビュー | `impl-review` | `/code-review` + 親 |
| 7 | ドキュメントの更新 | `impl-docs` | 親（steering は `steering` スキルの差分モード） |
| 8 | 完了ゲートと完了報告 | `impl-complete` | 親 |

### 承認ゲート
- 工程 1 が終わったら、改修の記録の要点（仕様の変更、影響範囲、実装計画、テスト方針）を提示して**止まる**。承認の前に `packages/` を編集しない（hook でも止める）
- 人間が承認を明言したら、`status: approved` と `approved_at` を書き、工程 2 に進む。修正の指示があれば記録を直して再提示する
- エージェントが自分で `approved` にしない

### 再開するとき
セッションが変わった・「続けて」と言われたら、まず該当する改修の記録を開き、`status` と工程チェックリストを見て、**最初の未完了の工程から**再開する。前の工程が壊れた状態の上に積まない（型チェックと関係するテストが緑かを最初に確かめる）。

- 規模の判定で省いた工程は、`- [x] <工程> — 省略（S）` のように**理由付きで印を付ける**。未完了のまま残さない
- `status: done` の後に、人間のレビューで同じ改修への修正を頼まれたときは、`status: in_progress` に戻し、「検証結果」に「再開の記録（日付、頼まれた内容）」を書いてから、該当する工程からやり直す。別の改修に当たる内容なら、新しい改修の記録を作る

## 人間を止める条件（自律の例外）

- **仕様に関わる判断が分かれるとき**: ユーザーに質問する（`AskUserQuestion`。ユーザーの設定で別の質問ツールが指定されていれば、そちらを使う）。後戻りの大きい分岐だけ。それ以外は既存のパターンを基準に既定の案を選び、改修の記録に理由を残す
- **取り消せない・外に影響する操作の直前**: クラウドの DB（開発用・本番）のスキーマ変更やデータの一括変更（ローカルの Supabase は確認なしでよい）、デプロイ、シークレットの変更、メールの送信、`git reset --hard`、force push。テストが緑でも、消したデータや外への通信は戻せない
- **詰まったとき**: 同じ失敗を 2〜3 回試しても解消しない、ある修正が別のテストを壊し続ける、設計の前提が崩れた、レビューの差し戻しが 3 周しても消えない。粘らずに「状況・試したこと・選択肢」を渡す

## 規模の判定

| 規模 | 目安 | 進め方 |
| --- | --- | --- |
| XS | 誤字、コメント、定数や設定値だけ | このフローを使わずに編集してよい。改修の記録は作らず `CHANGELOG.md` の Unreleased にだけ書く。ただし公開 API（エンドポイント、shared のスキーマ）やビルド（依存、tsconfig、設定）に触れるなら S 以上 |
| S | 局所的なバグ修正、小さな UI やロジックの変更 | 全工程を軽く。改修の記録は短くてよい。**1b（仕様レビュー）と 3b（bug-reviewer）は省略し、6（`/code-review` の low）は必ず回す**。省いた工程はチェックリストに「省略（S）」と書く |
| M | 複数ファイル、API や型の変更 | 全工程。仕様レビューあり。TodoWrite で進捗を持ち、1 セッションで終わらないと判断したら、その時点の状況を改修の記録に書いてから止まる |
| L | 新しい機能、スキーマの追加、複数の機能にまたがる | 全工程を厚く。工程 3 は観点を分けて複数回。複数の機能にまたがるなら、先に `plan` スキルで計画書を作る |

## 承認なしで `packages/` を編集しないこと（spec-gate）

- `packages/` を編集してよいのは、次のどちらかがあるときだけ: `status: approved` / `in_progress` の改修の記録、または `status: approved` / `in_progress` の計画書で、編集するパスがその計画書の `scope:` に含まれるとき
- 計画書による許可は、**その計画の作業をしているときだけ**使える。別の改修のために、進行中の計画書（例: ハーネス移行計画の `scope: packages/**`）を理由に編集しない
- hook（`.claude/hooks/spec-gate.mjs`）が、根拠の無い `packages/` の編集で**人に確認を求める**。確認が出たら、自分の判断で進めず、その編集が何のためかを人に説明する
- **XS の編集**: ユーザーの依頼が XS に当たると判断したら、応答で「XS として改修の記録を作らずに編集します」と明言し、編集後に `CHANGELOG.md` の Unreleased に 1 行書く。spec-gate の確認が出るので、人が許可したら編集する（許可が無ければ S として改修の記録を作る）。判断に迷うものは S として扱う

## スコープ外

- **コミットと push**: ユーザーに頼まれたときだけ
- **リポジトリ全体の劣化の掃除**: 今回の変更と関係ない劣化（全体の未使用コード、依存の脆弱性）は、CI と定期的な掃除が担う。このフローは今回の変更の分だけを片付ける
- **`/code-review ultra`**: 課金されるため、自動では実行せず提案にとどめる
