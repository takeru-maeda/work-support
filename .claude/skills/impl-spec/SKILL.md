# 工程 1: 改修の記録の作成 → 承認の依頼

**入口条件**: 工程 0（`impl-investigate`）を終えていること。

## 手順

1. **バージョンを決める。** 今のバージョン（`packages/*/package.json`）と SemVer（`docs/guides/versioning.md`）から、この改修の次のバージョンを決める。`CHANGELOG.md` の Unreleased や、`status` が done 以外の改修の記録に、すでに予約されたバージョンがないかも確かめる。
2. **改修の記録を作る。** `docs/specs/_template/change.md` をコピーして、主な機能の `docs/specs/<feature>/changes/v<X.Y.Z>-<slug>.md` に置き、`status: draft` で書く。機能のフォルダが無ければ作る（`spec.md` が無い機能なら、その旨を背景に書き、工程 7 で `spec.md` を新しく作る）。
3. **各節を埋める。** 特に次を具体的に書く。
   - **手本にする既存コード**を `file:line` で 1〜2 例。どの構造、命名、エラー処理を踏襲するか。「既存に合わせる」は具体例が無いと機能しない
   - **影響範囲**: 変更する関数、型、定数、スキーマ、カラム、文字列 ID を grep して、参照している箇所をすべて洗い出す（ファイルが近いかで決めない）。api / web / shared の両側、テスト、仕様書、steering まで
   - **受け入れ基準**: 3〜7 個。正常系、異常系、境界、非機能を含める。`AC-<feature>-NN` の ID を振る（既存の番号は振り直さない）。これが工程 2 の Red テストと、工程 3 の判定基準になる
   - **UI の方針**（UI を変えるとき）: 手本の画面、流用する部品、新しく共通化する部品、3 幅のレスポンシブの方針、工程 0 で確認した今の画面の様子。`frontend-design` スキルを読み込んで方針を決める
   - **代替案とトレードオフ**: 判断が分かれる点があるときだけ。推奨案と理由を書く
4. **工程チェックリスト**の「0」「1」に印を付ける。
5. **仕様レビュー（M 以上）**: `spec-reviewer` エージェントに、改修の記録のパスと、関係する `spec.md` のパスだけを渡す（作った意図は渡さない）。返ってきた指摘を親が確かめ、正しいものは記録に反映する。誤りと判断したものは理由を控える。チェックリストの「1b」に印を付ける。
   - **S のときは省略し、`- [x] 1b. 仕様レビュー — 省略（S）` と理由付きで印を付ける**（印が無いと、再開のときにここで止まる）
6. **承認を依頼して止まる。** 次の形で提示する。

```
## 承認のお願い: <改修の名前>（v<X.Y.Z>、規模 <S/M/L>）
改修の記録: docs/specs/<feature>/changes/v<X.Y.Z>-<slug>.md

- 目的: …
- 仕様の変更: 追加 / 変更する AC の要点
- 影響範囲: …
- 実装計画: 手本、作る / 変えるファイル、方針
- テスト方針: …
- 判断してほしい点: （あれば。推奨案と代替案）
```

## 出口条件

- 改修の記録が `status: draft` で揃い、承認を依頼した状態で**止まっている**
- 人間が承認を明言したら、`status: approved`、`approved_at` を書き、チェックリストの「★ 承認」に印を付けて、**`impl-tdd`（工程 2）** を読み込む
- 修正の指示があれば、記録を直して再提示する
