# 工程 8: 完了ゲート → 完了報告

**入口条件**: チェックリストの「7」に印があること。

## 完了ゲート（すべて満たして初めて完了）

1. **受け入れ基準をすべて満たしている。** AC ごとに、どのテストまたは確認で満たしたかを言える
2. **最後にもう一度、全部回して緑。** 影響するパッケージすべての型チェック、lint（今回触ったファイル）、影響範囲のテスト、ビルド（web は `pnpm --filter web build`。api にはビルドの手順が無いので型チェックまで。shared を変えたら api と web の両方の型チェック）。工程 5〜7 で修正が入っているので、前の緑を流用しない
3. **bug-reviewer（工程 3。S は省略）と `/code-review`（工程 6）の、改修範囲の Critical / Major がゼロ。** 残っているなら正直に書く
4. **ドキュメントの更新先を 1 つずつ言い切った**（「更新した / 不要（理由）」）。まとめて「ドキュメント更新済み」で済ませない
5. **UI の変更は、3 幅の確認と手本との比較を済ませた**
6. 差分に、デバッグ用のログ、一時ファイル、無関係な変更が混ざっていない（`git status` と `git diff --stat` で確かめる）

## 改修の記録を閉じる

- 「検証結果」を書き終える（実行したコマンドと結果、スクリーンショット、指摘と対応、見送った Minor、ドキュメントの更新先ごとの結果）
- 工程チェックリストの「8」に印を付け、`status: done`、`completed_at` を書く

## 完了報告

後から読んでわかる要点だけを、次の形で残す。

```
## 完了: <改修の名前>（v<X.Y.Z>）
改修の記録: docs/specs/<feature>/changes/v<X.Y.Z>-<slug>.md

- 作ったもの: …
- 主な判断: 承認後に自分で決めたこと、選んだトレードオフ、計画からの変更
- 変更したファイル: …
- 検証: 実行したコマンドと結果の要約（UI はスクリーンショット）
- ドキュメント: 更新先ごとの結果
- 見送った指摘: …
- 次の一手: 範囲外の指摘、人間に判断してほしいこと、コミットしてよいか
- ハーネス改善の提案: （下の節）
```

## ハーネス改善の提案（必ず考える）

今回の作業で、ハーネス（CLAUDE.md、steering、rules、スキル、hooks、lint、テスト）に不具合や穴は無かったかを振り返る。

- 工程 3 や 6 の指摘のうち、**既存の規約や手本で本来防げたはずのもの**
- hook の誤検知や見逃し、古くなっていた文書、スキルの手順の穴、遅い・不安定なテスト
- 人間からの指摘（レビュー、途中の修正指示）

見つかったら `docs/harness/improvements.md` に 1 行足し、完了報告で提案する。**直し方は性質で選ぶ**: 機械的に判定できるものは lint、テスト、hook（優先）、判断が要るものは steering、rules、スキル、手本の追加。勝手に適用せず、提案して人間の判断を待つ（明らかな誤字や、パスの誤りの修正はその場で直してよい）。

何も無ければ「ハーネス改善の提案: なし」と書く。
