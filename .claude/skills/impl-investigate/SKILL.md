# 工程 0: 仕様の把握

**入口条件**: autonomous-impl から呼ばれていること。改修の記録はまだ無くてよい（あれば開いて状態を確かめる）。

## 手順

1. **依頼を読み、わからない前提をここで解消する。** 実装の途中で聞き返すのは高くつく。後戻りの大きい分岐だけをユーザーに質問し（`AskUserQuestion`。ユーザーの設定で別の質問ツールが指定されていればそちら）、それ以外は既存のパターンを基準に決める。
2. **バグのときは、仮説を立てる前に `docs/specs/incidents.md` を引く。** 症状に近い行から、該当する `docs/specs/<feature>/spec.md` の「設計不変条件」と「ポストモーテム」を読む。grep や Explore より先に行う。バグは見えている症状が原因を取り違えさせやすい。
3. **関係する仕様書を読む。** `docs/specs/<feature>/spec.md`（まだ無い機能は `docs/legacy/specs/` を参考にし、コードを正とする）。関係する steering の節も読む。
4. **影響範囲のあたりを付ける。** 触るファイル、層、パッケージ（api / web / shared）。広く読む必要があるときは `Explore` に任せ、**結論（触るファイル、手本の `file:line`）だけを受け取る**。grep の生ログでメインのコンテキストを埋めない。
5. **ライブラリの正しい使い方を、設計の前に確かめる。** 外部のライブラリやフレームワークに関わり、確信が持てない・バージョンに依存する箇所があるとき:
   - まず `package.json` と `pnpm-lock.yaml` で**実際に入っているバージョン**を確かめる（記憶やネットの「最新版」を基準にしない）
   - `mcp__context7__resolve-library-id` → `mcp__context7__query-docs` で、そのバージョンの使い方を確かめる。見つからなければ公式ドキュメントをネットで調べる
   - 確かめた要点は、工程 1 で改修の記録の「確認したライブラリの使い方」に書く
6. **UI を変えるとき**は、ここで `docs/steering/ui-design.md` を読み、`packages/web/CLAUDE.md` の「UI 変更の手順」の 1〜2（今の画面を Playwright MCP で確認）まで済ませる。

## 出口条件

- 改修の目的、関係する仕様書、影響範囲のあたり、ライブラリの確認結果が手元にそろっている
- 次は **`impl-spec`（工程 1）** を読み込む。改修の記録を作ったら、工程チェックリストの「0. 仕様の把握」にも印を付ける
