# 工程 7: ドキュメントの更新（親が担当し、任せない）

**入口条件**: チェックリストの「6」に印があること。

変更の意図、トレードオフ、どこをどう変えたかを知っているのは、実装した親エージェント自身。サブエージェントに任せると「なぜそうしたか」が落ちる。対象は**今回の変更に関係する範囲だけ**。

## 手順

更新先の一覧は、パッケージの `CLAUDE.md`「ドキュメントの更新先」が正本。それぞれについて次を行う。

1. **`docs/specs/<feature>/spec.md` を現在の姿に更新する。**
   - 改修の記録の「仕様の変更」を本文に反映する（受け入れ基準、画面と API、データ、設計不変条件、エラー時の挙動、テストとの対応）
   - frontmatter の `updated` / `code`（`パス :: シンボル`）/ `related` / `symptoms` を実態に合わせる
   - 「変更履歴」に 1 行足し、改修の記録へリンクする
   - `spec.md` がまだ無い機能なら、`docs/specs/_template/spec.md` から作り、`docs/specs/README.md` の一覧を更新する
   - 複数の機能にまたがる改修なら、ほかの機能の `spec.md` の変更履歴からもリンクする
2. **バグ修正なら、再発を仕組みで防ぐ 3 点をそろえる。**
   - `spec.md` の「ポストモーテム」に 1 件追記（日付、症状、真因、対策、再発時に確認すること）
   - `docs/specs/incidents.md` に 1 行追加し、frontmatter の `symptoms` に症状を足す
   - 再発防止のテスト（工程 2 の Red で足したものを指せばよい）
3. **`CHANGELOG.md` の Unreleased** に、利用者から見た変更を 1 行で書き、改修の記録へリンクする。
4. **steering**: 更新が必要かを判断する。
   - 必要なのは、新しいパターンや規約を持ち込んだ、技術を変えた、steering の記述が誤りになった、のどれかのときだけ
   - 必要なら **`steering` スキルを差分モードで呼び**、改修の記録と変更ファイルの一覧を渡す
   - 既存のパターンに沿っただけなら「不要」とする（多くの改修はこれに当たる）
   - 1 つの機能だけの振る舞いや設計は steering ではなく `spec.md` に書く（steering が膨らむのを防ぐ）
5. **`docs/testing/manual-checklist.md`**: 手動でしか確かめられない挙動（PWA、端末依存、メールの実受信など）が増減したら更新する。
6. 関係する `.claude/rules/` や パッケージの `CLAUDE.md` の記述が誤りになっていたら直す（ハーネスの更新として完了報告にも書く）。

## 出口条件

- 更新先ごとに「更新した / 不要（理由）」を改修の記録の「検証結果」に書いた
- チェックリストの「7」に印を付け、**`impl-complete`（工程 8）** を読み込む
