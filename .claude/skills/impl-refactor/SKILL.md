# 工程 5: リファクタリング（省略しない）

**入口条件**: チェックリストの「4」に印があること。

「ただ動くだけのコード」で終わらせないための工程。**一般的なコードの臭いの改善は、この工程がまとめて引き受ける**（工程 3 の bug-reviewer は扱わない）。今回の改修の文脈（設計の判断、危ない箇所）を持っている親エージェントが行い、サブエージェントには任せない。

## 手順

1. **`refactor` スキルを読み込む。** 臭いの一覧（長い関数、重複、巨大なクラス、深い条件分岐、マジックナンバーなど）で、今回の差分にある臭いを**名指し**し、対応する変換（関数の抽出、ガード節、定数化など）を当てる。最後に同じスキルのチェックリストで確かめる。
2. 見る観点:
   - 責務の分離、ファイルや関数の分け方（`docs/steering/structure.md` の置き場所に沿っているか）
   - 重複の抽出（web で同じ UI が 2 か所にあれば共通部品へ。`docs/steering/ui-design.md`）
   - 意図が伝わる名前、定数化、型の安全さ（`any` や無理な型変換が無いか）
   - React なら `vercel-react-best-practices` の該当ルール、合成の設計なら `vercel-composition-patterns`（Next.js 専用のルールは使わない）
3. **今回の作業で散らかしたものを片付け、差分をそのままレビューに出せる状態にする。**
   - 入れたデバッグ用のログ（`console.log` など）、一時ファイル、使わなくなったコードとファイルを消す
   - 消したコードへの参照が残っていないかを、設定ファイル（`wrangler.jsonc`、`vite.config.ts`、`tsconfig`）、`package.json` の scripts、ドキュメントまで追う
   - コードと合わなくなったコメントを直す
4. **変換を 1 つ当てるたびに、影響範囲のテストが緑のままであることを確かめる。** テストが緑であることが、振る舞いを変えていないことの保証になる。
5. 今回の変更と関係ない箇所の改善は広げない。気づいたものは完了報告の「次の一手」に書く。

## 出口条件

- 臭いを名指しして直した（または「臭いなし」と判断した理由がある）
- 片付けが済み、影響範囲のテストと型チェックが緑
- チェックリストの「5」に印を付け、**`impl-review`（工程 6）** を読み込む
