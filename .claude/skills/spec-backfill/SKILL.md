# 既存機能の仕様書への変換（P5）

ゴールは、**改修の前に読めば、壊してはいけないものがわかる仕様書**。旧ドキュメントの写しではなく、**今のコードの振る舞い**を正として書く。コード（`packages/`）は変えない（食い違いやバグを見つけても、ここでは直さない）。

## 入口

- 対象の機能は、計画書（`docs/plans/active/harness-migration.md`）の P5 の表から 1 つ選ぶ。順番は P6 の優先順（effort-ingest-gas → effort-draft → goals → weekly-report → その他）
- 機能の範囲（どの画面、どの API、どのテーブル）が表の説明とずれていそうなら、書き始める前にユーザーに確かめる
- すでに `spec.md` がある機能（platform、profile など、改修のときに一部だけ作ったもの）は、既存の受け入れ基準と不変条件の ID を残して、足りない節を埋める

## 手順

### 1. 材料を集める

- **旧ドキュメント**: `docs/legacy/specs/` の該当する節だけを読む（要件は `requirements/index.md`、設計は `design/` の 03 画面、05 API、06 データ構造、08 ロジック、09 DB など）。全体を読み込まない
- **コード**: 画面（`packages/web/src/pages`、`features/<feature>`。API の呼び出しは `features/<feature>/api/` と `api/`）、API（`packages/api/src/features/<feature>`）、スキーマ（`packages/shared/src/schemas`）。広く読むときは `Explore` に任せ、「条件 → 結果の振る舞いの一覧、エラー時の挙動、状態の置き場所、関係するシンボル（`パス :: シンボル`）」を結論だけ受け取る
- **全体像**: `docs/reference/api.md`（エンドポイント）、`docs/reference/database.md`（テーブル）
- **履歴**: `git log --format='%h %ad %s' --date=short -- <関係するパス>`。`fix` や「修正」のコミットは、ポストモーテムの候補として中身を読む
- **既存のテスト**: 関係する `*.test.ts(x)`、`*.int.test.ts`、`packages/e2e/tests/`

### 2. 照合する

旧ドキュメントとコードを、振る舞いの単位で突き合わせ、次の表を作る（`v1.0.7-baseline.md` の「照合の結果」に残す）。

| 項目 | 旧ドキュメント | コード | 扱い |
| --- | --- | --- | --- |

- **コードを正とする**。旧ドキュメントにだけある振る舞いは書かない（「旧ドキュメントにあるが実装されていない」として記録に残す）
- 食い違いのうち、**どちらが意図なのか判断できないもの**（コードのほうがバグかもしれない）は「要確認」にして、手順 7 で人間に聞く
- **「コードが実際にどう動くか」がわからないだけのものは、要確認にせず確かめる**。api はローカルの Supabase で `app.request` を使った使い捨てのテストを書いて動かし（確かめたら消す）、web は `pnpm dev:local` と Playwright MCP で試す。要確認にするのは「意図」がわからないものだけ
- 明らかな不具合を見つけたら、`spec.md` の「既知の落とし穴」に書き、計画書の P6 に「直す」項目として足す（受け入れ基準は今の振る舞いのまま書き、不具合であることを添える）

### 3. `spec.md` を書く

`docs/specs/_template/spec.md` から作る。節の順番と名前は変えない（当てはまらない節は「該当なし」）。

- **受け入れ基準**: `AC-<feature>-NN`。条件と結果がテストで確かめられる形で書く（「適切に」「正しく」は使わない）。正常系、異常系、境界、非機能
- **設計不変条件**: コードの中の「壊すと何かが起きる」決まり（競合の判定、合計の制約、ユーザー ID の条件など）。**破ると何が起きるか**を必ず書く。git の履歴のバグ修正は、不変条件の手がかりになる
- **画面と API**: 画面はルートと主な操作。API の入出力の詳細は書き写さず、`docs/reference/api.md` へのリンクとスキーマのファイル名にする（一覧を二重に持たない）
- **データ**: テーブルの列を書き写さず、`docs/reference/database.md` へのリンクと、この機能にとって大事な点（どの列で何を判定するか）だけ
- **テストとの対応**: 既存のテストがある AC はそのテスト、無い AC は「未（P6）」
- frontmatter の `code`（`パス :: シンボル`）、`related`、`symptoms`（利用者の言葉で）

### 4. 移行時点の記録を書く

`docs/specs/<feature>/changes/v1.0.7-baseline.md` を `docs/specs/_template/change.md` から作る。

- frontmatter: `version: v1.0.7`、`status: done`、`size` は空、`created` と `completed_at` は作った日、`released_in: v1.0.7`
- 「背景と目的」: 移行時点の姿の基準であること
- 「経緯」: git の履歴の要約（いつ、何が入り、何が直ったか。コミットのハッシュを添える）
- 「照合の結果」: 手順 2 の表と、要確認の一覧
- 工程チェックリストの節は消してよい（実装の工程は無い）

### 5. 過去のバグ修正を登録する

git の履歴に、利用者に見える症状のあったバグ修正があれば、次の 2 つをそろえる。

- `spec.md` の「ポストモーテム」に 1 件（日付、症状、真因、対策、再発時に確認すること。改修の記録の代わりにコミットのハッシュ）
- `docs/specs/incidents.md` の表に 1 行、frontmatter の `symptoms` にも症状を足す

### 6. 独立した目で点検する

`spec-reviewer` に、`spec.md` と `v1.0.7-baseline.md` のパスだけを渡し、「受け入れ基準と不変条件がコードと一致しているか（コードの `file:line` を根拠に）、書き漏れている振る舞いが無いか、AC がテストで確かめられる形か」を見てもらう。作った意図は渡さない。正しい指摘は反映し、退けたものは理由を記録に残す。

### 7. 人間に確かめる

次の形で報告して止まる。要確認が多いときは、後戻りの大きいものだけを質問ツールで聞き、残りは報告に並べる。

```
## 仕様書を作りました: <feature>
- spec.md: …（AC の数、不変条件の数、ポストモーテムの数）
- 照合の結果: 旧ドキュメントとの食い違い N 件（うち要確認 M 件）
- 要確認: …（項目、旧ドキュメント、コード、推奨する扱い）
- 見つけた不具合: …（計画書の P6 に足したもの）
```

人間の答えを `spec.md` と記録に反映したら、計画書の P5 の表の「spec」に印を付ける（「レビュー」の印は人間が付ける）。`docs/specs/README.md` の一覧も更新する。

## 守ること

- コード（`packages/`）は変えない。テストも書かない（P6 で書く）
- 仕様書は日本語で、利用者の言葉と実装の言葉を分けて書く（画面の文言はそのまま引用する）
- 推測で書かない。コードで確かめられなかった振る舞いは「要確認」にする
