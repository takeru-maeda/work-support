# 工程 4: 動作検証

**入口条件**: チェックリストの「3」に印があること。

## 原則: 成功は静かに、失敗だけを詳しく

テストは `--reporter=dot` のように、通ったテストの詳細を出さない形で回す。緑のログをコンテキストに積むと、設計や指摘といった持ち続けたい文脈が先に押し出される。

## 手順

1. **影響範囲を、参照からたどって決める。** ファイルが近いかで決めない（テストの更新漏れの主な原因）。識別子、定数、文字列 ID、関数や型のシグネチャ、スキーマ、カラムを削除・改名・値変更したとき、または関数の挙動（検証、受け付ける条件、戻り値）を変えたときは、**古い名前と変えた関数名をリポジトリ全体で grep し**（対象パスはパッケージの `CLAUDE.md`「参照 grep の対象パス」。api / web / shared の両側、本体とテストの両方）、残っている参照がないことと、すべての呼び出し元を確かめる。
2. **新しく書いたテストと、grep で見つかった既存のテストを実際に実行する。** 読んだだけで省略しない。
3. **型チェックとビルド**を、影響するパッケージすべてで回す。web は型チェックと `pnpm --filter web build`、api はビルドの手順が無いので型チェックだけ、shared を変えたら api と web の両方の型チェック。
4. **E2E**: Playwright の E2E が整っていれば（移行計画の P4 以降）、影響する画面のシナリオを回す。
5. **UI を変えたときは、実際に起動して画面で確かめる。**型が通った・描画された、で UI の完了としない。
   - 開発サーバーを起動し、Playwright MCP で該当の画面を開く
   - **375px / 768px / 1280px の 3 幅**でスクリーンショットを撮る。テキストの折り返し、はみ出し、重なり、横スクロール、ボタンのつぶれ、長い文字列での崩れを見る
   - 手本の画面と並べ、横幅、左右の余白、間隔、トーン、主な操作の位置がそろっているかを確かめる
   - 読み込み中、0 件、エラーの表示も確かめる
   - 崩れていたら、改修の記録の UI の方針に照らしてその場で直し、もう一度撮る。方針そのものが誤っていたときだけ、工程 1 の判断に戻る（人間に確かめる）
   - スクリーンショットは改修の記録から参照できるように保存し、一時ファイル（`.playwright-mcp/` など）は残さない
6. **API を変えたとき**は、テスト用 DB の仕組みが整っていれば `app.request` の結合テストで確かめる。整っていなければ、確かめられなかったことを記録に書き、人間に確認方法を提案する（本番の API や本番の DB で試さない）。

## 出口条件

- 影響範囲のテスト、型チェック、ビルドがすべて緑。UI の変更は 3 幅で確認済み
- 実行したコマンドと結果、スクリーンショットを改修の記録の「検証結果」に書いた
- チェックリストの「4」に印を付け、**`impl-refactor`（工程 5）** を読み込む
