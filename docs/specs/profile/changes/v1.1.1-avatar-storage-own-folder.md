# プロフィール画像の保存先の権限を、本人のフォルダだけに絞る

## 背景と目的

- プロフィール画像は Supabase Storage の `avatars` バケットに、`<ユーザー ID>/avatar.<拡張子>` の名前で置いている（`packages/web/src/lib/storage.ts:22`）。アップロードと古い画像の削除は、**ブラウザから本人のアクセストークンで直接** Storage を呼んでいる
- 今の storage ポリシー（本番と同じ。`20261013000000_baseline.sql:780-783`）は、条件が「`avatars` バケットであること」だけ。**ログインしている人なら誰でも、他人の画像を上書き・削除・別の場所へ移動でき、他人のフォルダの一覧も取れる**。ブラウザの開発者ツールから anon キーと自分のトークンを使えば、画面を通さずにできる
- **成功の条件**: 本人のフォルダ（`<自分のユーザー ID>/`）の中だけ、アップロード・上書き・削除・一覧ができる。他人のフォルダやフォルダの外には何もできない。画面の今の使い方（アップロード、上書き、古い画像の削除、アカウント削除のときの後始末、公開 URL での表示）は今までどおり動く

`profile` 機能の `spec.md` はまだ無い（ハーネス移行計画の P5）。工程 7 で、この改修の範囲（プロフィール画像の保存）を中心に新しく作る。

## 仕様の変更

- 追加: **AC-profile-01**: ログインしたユーザーは、自分のフォルダ（`avatars/<自分のユーザー ID>/`）に画像をアップロードでき、同じ名前で上書き（upsert）もできる
- 追加: **AC-profile-02**: 他人のフォルダや、フォルダの外（バケットの直下）へのアップロードは拒否される。ログインしていない状態でのアップロードも拒否される
- 追加: **AC-profile-03**: 他人のフォルダにある画像は、上書き・削除・自分のフォルダへの移動や複製ができず、元の場所に元の中身のまま残る
- 追加: **AC-profile-04**: 自分のフォルダの画像は削除できる（画像を差し替えたときに古い画像を消す処理）
- 追加: **AC-profile-05**: 他人のフォルダの一覧（`list`）を取っても、中身は返らない。ログインしていない状態でも同じ
- 追加: **AC-profile-06**: 画像は公開 URL（`getPublicUrl`）で、ログインしていなくても誰でも表示できる（今までどおり。バケットが公開のため）
- 追加: **AC-profile-07**: プロフィール画像を設定したユーザー（`user_metadata.avatarUrl` が `avatars/<自分の ID>/...` の公開 URL）がアカウントを削除すると、`<自分の ID>/` の画像がすべて消える（API が service role で消す。今までどおり）。`avatarUrl` が無いか本人のフォルダを指していないときは画像を消さない（今の挙動。対象外を参照）
- 追加: **AC-profile-08**: 自分の画像を、他人のフォルダやバケットの直下へ移動・複製することはできず、元の場所に元の中身のまま残る
- 不変条件の追加:
  - **INV-1**: ブラウザ（`authenticated` のロール）から触れる Storage のオブジェクトは、パスの最初のフォルダが自分のユーザー ID（`auth.uid()`）と一致するものだけ。INSERT / UPDATE / DELETE / SELECT のすべてに同じ条件をかけ、UPDATE は移動先（`WITH CHECK`）にもかける。破ると、他人のプロフィール画像を差し替えたり消したりできる

## 影響範囲

- **参照箇所**:
  - `avatars` バケットを使うのは 2 か所だけ。web の `src/lib/storage.ts`（`uploadAvatarImage`: `<userId>/avatar.<ext>` に upsert。`deleteAvatarImage`: 渡されたパスを削除）と、api の `src/features/users/service.ts`（アカウント削除のとき、service role で `<userId>/` を一覧して削除）
  - web の削除は `features/profile/hooks/modules/useAvatarUpload.ts` から呼ぶ。消すのは、今アップロードした画像（保存に失敗したとき）か、`user.avatarUrl` から取り出した古い画像のパスで、どちらも本人のフォルダ
  - 保存先の名前の形（`${userId}/avatar.${extension}`）は、ファイルを作ったとき（e641053、2025-10-22）から変わっていない。本番の画像はすべて本人のフォルダにある見込み
- **機能**: profile（プロフィール画像、アカウント削除）
- **API と shared のスキーマ**: 変更なし
- **DB**: `storage.objects` のポリシー 4 つを作り直す新しいマイグレーション（テーブルとカラムは変えない）。生成型 `db.ts` と `docs/reference/database.md` は public スキーマだけなので変わらない
- **画面**: 変更なし（正しい使い方の挙動は同じ）
- **テスト**: 既存のテストへの影響なし（web の部品テストと E2E にアバターの操作は無い）。新しく Storage の権限の結合テストを足す
- **アカウント削除との関係**: 画像の持ち主（owner）のユーザーも Auth から削除できることを、ローカルの Supabase（CLI 2.120）で確かめた（2026-10-14）。ファイルは残るので、今の `deleteCurrentUserAccount` の順序（ユーザーを消してから画像を消す）のままでよい
- **ドキュメント**:
  - `docs/specs/profile/spec.md` を新しく作り、`docs/specs/README.md` の一覧を更新する
  - `docs/reference/database.md` の前提: 「ポリシーは 0 個」は public スキーマの話なので、ストレージだけはブラウザから直接触り、ポリシーで本人のフォルダに絞っていることを書き分ける（手書きの欄）
  - `docs/steering/security.md`: 「service role で接続するので RLS に守られない」の例外として、ブラウザから直接触る Storage はポリシーが唯一の守りであることを 1〜2 行足す
  - `CHANGELOG.md`、ハーネス移行計画（P3 の残りの項目）
  - ポストモーテムと `docs/specs/incidents.md`: 不要（利用者が気づく症状が出た不具合ではなく、悪用された形跡も確かめようがない権限の穴のため。再発防止テストは新しい結合テストで満たす）

## 実装計画

- **手本にする既存コード**:
  - SQL: `packages/api/supabase/migrations/20261013010000_populate_projects_with_tasks_mv.sql`（基準のマイグレーションのあとに足す、小さな修正のマイグレーション。冒頭のコメントで理由を書く）
  - テスト: `packages/api/test/gas-effort.int.test.ts`（`createTestUser` で一意なユーザーを作る結合テスト）
- **新しく作るファイル**:
  - `packages/api/supabase/migrations/<日時>_restrict_avatar_storage_to_own_folder.sql`: 今の 4 つのポリシーを `DROP POLICY IF EXISTS` で消し、本人のフォルダに絞った 4 つを作る

    ```sql
    -- 条件（4 つ共通）: bucket_id = 'avatars' AND (storage.foldername(name))[1] = (select auth.uid()::text)
    CREATE POLICY ... FOR SELECT TO authenticated USING (<条件>);
    CREATE POLICY ... FOR INSERT TO authenticated WITH CHECK (<条件>);
    CREATE POLICY ... FOR UPDATE TO authenticated USING (<条件>) WITH CHECK (<条件>);
    CREATE POLICY ... FOR DELETE TO authenticated USING (<条件>);
    ```

  - `packages/api/test/avatar-storage.int.test.ts`: 2 人のテスト用ユーザーを作り、ブラウザと同じ形（anon キー + 本人のアクセストークンの supabase-js）で Storage を呼んで AC-profile-01〜07 を確かめる
- **変更するファイル**:
  - `packages/api/test/helpers.ts`: テスト用ユーザーとしてログインした supabase-js のクライアントを返す小さな関数を足す（Storage をブラウザと同じ権限で呼ぶため）
  - 基準のマイグレーションの TODO のコメントは書き換えない（既存のマイグレーションは編集しない規約）
- **設計の方針**:
  - 権限の判定は DB（RLS のポリシー）だけに置く。web のコードは変えない（ブラウザ側で守っても、直接呼ばれれば意味がない）
  - SELECT も本人のフォルダに絞る。上書き（upsert）とアップロード直後の結果の返却に SELECT が要るため、無いとアップロードが失敗する。画像の表示は公開 URL で、ポリシーを通らないので影響しない
  - ポリシーの名前は、意味がわかる名前に付け直す（今の名前は Supabase の画面の自動生成の `... 1oj01fe_0`）
- **代替案とトレードオフ**:
  - SELECT は今のまま（バケット全体を読める）にする案: 他人のフォルダの一覧（ファイル名）が取れるままになる。公開 URL で表示は誰でもできるので実害は小さいが、絞っても困ることが無いので絞る（推奨）
  - バケットを非公開にして署名付き URL で表示する案: 画面とアバターの URL の保存の仕方が変わり、範囲が大きい。今回は対象外
- **確認したライブラリの使い方**（Supabase、Context7 の `/supabase/supabase`。Storage のアクセス制御のガイド）:
  - 本人のフォルダの判定は `(storage.foldername(name))[1] = (select auth.uid()::text)`。`auth.uid()` を `select` で包むと、行ごとではなく 1 回だけ評価される
  - アップロードは INSERT、上書き（upsert）は加えて SELECT と UPDATE が要る。アップロードの結果を返すのにも SELECT が要り、無いと「new row violates row-level security policy」で失敗する
  - 公開バケットの公開 URL での読み出しは、ポリシーを通らない

## テスト方針

- AC ごとの結合テスト（ローカルの Supabase。`pnpm test:int`）。テストで置いたファイルは、テストの後で service role で消す（ユーザーを消してもファイルは残るため）:
  - AC-profile-01: 自分のフォルダへのアップロードと、同じ名前での上書き
  - AC-profile-02: 他人のフォルダ、バケットの直下、ログインしていない状態でのアップロードがエラーになる
  - AC-profile-03: 他人の画像への上書き・削除・自分のフォルダへの移動と複製がエラーまたは空振りになり、相手の画像が元の中身のまま残る（service role で中身を確かめる）
  - AC-profile-08: 自分の画像の、他人のフォルダとバケットの直下への移動と複製がエラーになり、元の場所に元の中身のまま残る（移動先の判定が UPDATE の `WITH CHECK` と INSERT の条件のどちらで行われるかは、テストからは区別できない。どちらも同じ条件なので、どちらで止まってもよい）
  - AC-profile-04: 自分の画像を削除でき、消えている
  - AC-profile-05: 他人のフォルダの一覧が、ログインした他人からも、ログインしていない状態からも空
  - AC-profile-06: 公開 URL をログインなしで取得でき、中身が一致する
  - AC-profile-07: 画像を置き、`user_metadata.avatarUrl` にその公開 URL を設定した（admin の `updateUserById`。web の `updateProfile` と同じ形）ユーザーを `DELETE /api/users/me` で削除すると、フォルダの画像が消える
- 先に AC-profile-02 / 03 / 05 / 08 が今のポリシーで落ちること（Red）を確かめてから、マイグレーションを書く
- **ローカルの DB への適用は人間に頼む**（規約で、テスト用の DB を含めてエージェントは DB に適用しない）。マイグレーションを書いたら止まり、`pnpm exec supabase migration up --local --workdir packages/api` の実行を依頼する。適用のあとで Green を確かめる。CI はまっさらな DB にすべてのマイグレーションを流してから回るので、そこでも確かめられる
- 既存の挙動の確認: E2E とその他の結合テストが通ること

## 本番と開発用への適用（人間が行う）

マイグレーションは、エージェントはクラウドの DB に適用しない。コミットのあと、人間が次の順で行う。

1. **開発用**（基準のマイグレーションから作り直したので、マイグレーションの履歴がある）: `pnpm exec supabase db push --db-url "<開発用の接続文字列>" --workdir packages/api`。画面でプロフィール画像の変更を確かめる
2. **本番の事前の確認**（読み取りだけ）: 本人のフォルダの外にある画像が無いかを、SQL エディタで確かめる。あれば、ポリシーを変えたあと本人が上書き・削除できなくなるので、適用の前に相談する

    ```sql
    select name, owner_id from storage.objects
    where bucket_id = 'avatars'
      and (storage.foldername(name))[1] is distinct from owner_id;
    ```

    `owner_id` の列が無い古い版なら、`owner::text` に置き換える。

3. **本番**: マイグレーションの履歴に基準のマイグレーションが入っていないと、`db push` は基準のマイグレーションから流そうとして失敗する。先に `supabase migration list --db-url "<本番>"`（読み取りだけ）で履歴を確かめ、無ければ、新しいマイグレーションの SQL だけを SQL エディタで実行する。そのときは `begin;` と `commit;` で包み、ポリシーが 0 個の瞬間や、途中で失敗したまま残ることを避ける（履歴をそろえる `migration repair` は別途相談）
4. **適用の結果の確認**（どちらの環境も）: マイグレーションの最後の検査が、avatars に触れる古いポリシーの残りを見つけるとエラーで止まり、全体が取り消される（エラーの文に残ったポリシーの名前が出る）。通ったら、読み取りだけで `select policyname, cmd from pg_policies where schemaname = 'storage' and tablename = 'objects';` を実行し、avatars のポリシーが新しい 4 つ（`Users can ... their own avatars`）だけであることを確かめる。そのあと画面で、プロフィール画像の設定と差し替えを試す

## 対象外

- バケットを非公開にする、ファイルの種類やサイズの上限をバケットに設定する（今は画面で `image/*` だけを受け付けている）
- アップロードと削除を API 経由に移す
- 基準のマイグレーションの TODO のコメントの修正（既存のマイグレーションは編集しない）
- `avatarUrl` のメタデータが無いユーザーを削除したとき、フォルダに残った画像を消すこと（今の挙動のまま）
