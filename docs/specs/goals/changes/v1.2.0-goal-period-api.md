# 目標の期間をまとめて作る API にする

## 背景と目的

- 目標の追加は、画面が 1 件ずつ `POST /api/goals` を送る。途中で失敗すると一部の目標だけが残り、重みの合計が 100 にならない期間ができる（goals の既知の落とし穴）
- 期間の前後、現在の期間との重なり、重みの合計は画面だけが確かめていて、API は確かめない（INV-1、INV-3、AC-goals-21）。`PUT` は期間の変更も受け付ける（INV-4、AC-goals-22）。画面を通らない呼び出しで、今の目標が黙って「過去」に回る
- MCP サーバーの `create_goal_period`（`docs/plans/active/mcp-server.md` の P3、D10）は、AI から期間を作る。その前提として、サーバーで確かめて全部作るか何も作らないかにする。プレビューでも同じ確認を使えるように、確認だけを行う関数を分ける
- 成功の条件: 期間の作成は 1 回の呼び出しで、確認に通らなければ何も作らない。画面の目標の追加も同じ API を使う

## 仕様の変更

- 追加: **AC-goals-23**: `POST /api/goals/periods` の本文は `{ start_date, end_date（YYYY-MM-DD）, goals: [{ title（文字列）, content（文字列。null や省略は不可）, weight（0 より大きく 100 以下の数値） }] }`（`goals` は 1 件以上 20 件以下。上限は 2026-10-16 の人間の判断で追加）。確かめ方は 2 段:
  - **形の確認**（Zod。外れたら入力の検証の失敗の形 `400 { data, error, success: false }`）: 項目の型、日付の形、`goals` が空か 21 件以上、`content` が null、重みが範囲の外
  - **業務の確認**（service。外れたら `AppError` の `400 { error: "<文>", accessLogId }`）: 次の順に確かめ、**最初に外れたものの文**を返す。文は画面と同じ
    1. 終了日が開始日より後（「終了日は開始日より未来の日付を選択してください。」）
    2. 開始日が、そのユーザーの現在の期間の終了日より後（「開始日は既存目標の終了日（yyyy/MM/dd）より未来の日付を選択してください。」）。目標が無ければ確かめない
    3. どの目標名も、前後の空白を除いて空でない（「目標名を入力してください。」）。保存するのは入力そのまま
    4. 重みを **1 行ずつ小数第 2 位に丸めた値**で、どの行も 0 より大きく、合計がちょうど 100.00（「重みの合計を100%にしてください。」。DB の列 `numeric(5,2)` が 1 行ずつ丸めて保存するため。33.333 / 33.333 / 33.334 は 99.99 で 400、0.004 は 0.00 で 400）
  - どちらかで外れたら何も作らない。通ったら、すべての目標を進捗率 0 で 1 つのトランザクションで作り、`201 { created: [...] }`（本文の順）を返す。履歴は残さない
- 追加: **AC-goals-24**: 同じユーザーが、重なる期間（例: 同じ期間）を同時に 2 回送ると、片方だけが 201 になり、もう片方は 400「開始日は既存目標の終了日（yyyy/MM/dd）より未来の日付を選択してください。」（日付は先に作られた期間の終了日）。目標は片方の分しか無い
- 廃止: **AC-goals-21**（`POST /api/goals`）。ルートを消す（画面の追加は AC-goals-23 を使う。1 件ずつ作る経路を残すと INV-1、INV-3 を破れる）
- 変更: **AC-goals-22**: 旧「`PUT` は `start_date` / `end_date` も受け付けて変える」→ 新「`PUT` の本文は `title`、`content`、`weight`、`progress` だけ。それ以外の項目（期間を含む）があれば、入力の検証の失敗の形の 400（`UpdateGoalRequestSchema` を知らない項目を拒む `z.strictObject` にする。今の画面の呼び出し元 `useGoalsTableManager.ts:111-115`、`useGoalContentDialog.ts:52` は期間もほかの項目も送っていないことを確かめた）」
- 変更: **AC-goals-13**: 旧「目標名が空でなく重みが 0 より大きい行だけを、1 行ずつ順に `POST /api/goals` で作る…途中で失敗したら…」→ 新「すべての行を `POST /api/goals/periods` で 1 回で送る（AC-12 で、どの行も重みが 0 より大きいときしか押せないので、外す行は無い）。目標名が前後の空白を除いて空の行があれば、送らずにトースト『目標名を入力してください。』を出す。API が 400 を返したら、その文（`error`）をトーストに出す。それ以外の失敗は今と同じ『目標の保存に失敗しました。時間を空けて再度お試しください。』。どの失敗でも何も作られておらず、入力は残る」。今の「有効な目標を入力してください。」の分岐は、たどり着けなくなるので消す
- 変更: **AC-goals-12**: 行が 20 行（`MAX_GOALS_PER_PERIOD`）になると「目標を追加」を押せない（2026-10-16 の人間の判断で追加）
- 不変条件の変更: **INV-1**、**INV-3**、**INV-4** の「守っているのは画面だけ」「API は確かめない」「API は変更を受け付ける」を、「API（AC-goals-23、22）で守る」に書き換える
- 既知の落とし穴から消す: 「目標名が空の行は黙って捨てられる」「追加の途中で失敗すると一部だけ残る」

- **設計の方針**:
  - service に `validateGoalPeriod(supabase, userId, request)` を置く。DB を読むのは「現在の期間の目標」だけで、返り値は「誤りの一覧」と「この期間を作ると編集できなくなる今の目標の一覧」。`POST /api/goals/periods` と、MCP の `create_goal_period` のプレビューの両方が使う
  - `createGoalPeriodService` は `validateGoalPeriod` で先に確かめ、通れば `create_goal_period` を 1 回呼ぶ。DB の関数の中でも、ユーザーごとのロック（`pg_advisory_xact_lock`）を取ってから、現在の期間の終了日と比べ直す（service の確認と作成の間に別の期間が作られる競合を防ぐ。AC-24）。重なっていたら、エラーコードを決めた例外の `detail` に、その終了日を入れて投げ、service が AC-23 の 2 の文に変える
  - 重みの合計、期間の前後、目標名は、DB を読まずに決まる入力だけの確認なので service だけで行い、DB の関数では比べ直さない（計画書 P3 の「DB の関数で重みの合計、期間の前後…」からの変更。同時の送信で結果が変わるのは「重なり」だけなので、ロックの中で比べ直すのはそれだけで足りる）
  - 合計の比較は、小数第 2 位に丸めた重みの合計が 100.00 か（DB の列が `numeric(5,2)` のため）
- **代替案とトレードオフ**:
  - `POST /api/goals` を残すか: 残すと INV-1、INV-3 を API から破れるので消す。⚠️ 古い web が新しい API に当たると目標の追加が失敗するので、リリースは web と API を同じ時に出す（`release-v1.1.md` の順番の決まりに書き足す）
- **確認したライブラリの使い方**: effort-entry v1.1.3 で確かめる `rpc` の例外の受け取り方と同じ

## テスト方針

- 結合（ローカルの Supabase）: DB の関数の権限（`browserClient` の anon と本人のトークンから `rpc('create_goal_period')` を呼ぶと拒まれる）、AC-23 の正常系（作った目標が進捗率 0、履歴なし、現在の目標になる）、各 400（形の確認と業務の確認のそれぞれ。終了日が前、現在の期間と重なる、目標名が空白だけ、重み 33.333 / 33.333 / 33.334、重み 0.004、合計 100.01、複数の誤りでは決まった順の最初の文）でどれも何も作られない、目標が無いユーザーは期間の前後だけ確かめる、AC-24（同じ期間を同時に 2 回送り、片方だけが 201、もう片方の文に先の期間の終了日が入る）、AC-22（`PUT` に期間を送ると 400）、`POST /api/goals` が無くなった（404）、トークンが無ければ 401、他人の期間は「現在の期間」に数えない
- 単体: `validateGoalPeriod` の誤りの組み合わせと、編集できなくなる目標の一覧
- 部品（web）: 追加の画面が 1 回だけ `POST /api/goals/periods` を送る。目標名が空の行があると送らずにトーストを出す。400 なら API の文、500 なら今の文を出し、入力が残る

- 重みの丸めは、浮動小数点の掛け算ではなく、送る 10 進の文字列の桁で四捨五入する（DB の `numeric(5,2)` と同じ結果にするため。33.33499999999999 を掛け算で丸めると 33.34 になり、DB は 33.33 で保存する）

- `validateGoalPeriod` のテストは、DB を読むので結合テストに置き、DB を読まない確認（`checkGoalPeriod`）を service の単体テストにした
