### 要確認

1. **週の境目を日本時間にしてよいか**: 今は UTC で計算するため、日本時間の月曜 0:00〜9:00 の更新が前週の分になる。週報も UTC の月曜 0:00 で区切っており、目標の画面と週報は今のところ同じ境目でそろっている。推奨: 日本時間（Asia/Tokyo）の月曜 0:00 を境目にする。目標の画面と週報を同じ改修でそろえて直す（P6 以降に改修の記録を通す）
2. **履歴の無い目標の前週の値を 0 にしてよいか**: 今は、前週より前に作って一度も更新していない目標は、前週の値が今の値になり、初めて進捗を入れた週の差分が 0 に見える。目標は進捗 0 で作られ、進捗の変更は必ず履歴を残す（INV-2）ので、履歴が無ければ前週の時点の値は 0 のはず。週報はこの場合 0 を使う。推奨: 0 にして週報とそろえる。ただし、履歴の仕組みより前に進捗を入れた古いデータが本番にあると、その目標の差分が大きく出る
3. **重み・期間のルールを API でも守るか**: 今は web の画面だけが守っている（逆の期間、既存の期間より前や重なる期間、作成後の期間の変更、重みの合計を、API は受け付ける）。追加と表の更新は 1 件ずつ送るので、途中で失敗すると一部だけ残り、追加の場合は同じ期間で追加し直すこともできなくなる。推奨: 期間の追加を「1 つの期間の目標をまとめて 1 回で作る」API にし、サーバーで期間の前後・重なり・重みの合計を確かめて、全部作るか何も作らないかにする。`PUT` は期間を受け付けないようにする。大きめの改修なので、P6 以降に改修の記録を通す

### 見つけた不具合（計画書の P6 に足すもの）

- 追加の画面で、重みだけ入れて目標名が空の行が、保存の時に黙って外される（重みの合計が 100 にならない）
- 表で編集中に、内容のダイアログの保存や削除をすると、表の編集中の値が元に戻る
- 内容のダイアログが失敗しても閉じて入力が失われる。保存中も押せる
- 過去の目標の検索: キーワードの `,` で 500、最後のページより先で 500、エラーのトーストが描画のたびに出続ける、並び順に同じ値があるとページをまたいで重複・抜けが出る
- `:id` が数字でないと 500
- `PUT` で `updated_at` が変わらない
- 表の「更新」で 2 件目以降が失敗すると、まだ保存していない編集が消える（1 件ごとの成功で一覧を取り直すため）
- 前週の進捗の履歴を件数の上限なしで取るので、`max_rows` を超えると今の目標の履歴から切り捨てられ、差分が黙って +0.0% になる
- 過去の目標の進捗率の絞り込みで、壊れた条件（下限 > 上限、範囲の外）が保存され、「クリア」するまで開くたびにエラーのトーストが続く
- 本文が空の `PUT` が、目標があっても 400 `Goal not found` になる

## 仕様レビュー（spec-reviewer）

- Major 2 件、Minor 11 件を受けて spec.md を直した。Major は、表の「更新」の途中で失敗したときに編集中の値が残るのは 1 件目の失敗だけであること（AC-05）と、前週の進捗の履歴が `max_rows` で切り捨てられて差分が黙って誤ること（既知の落とし穴）。Minor は、INV-2 と AC-10 の食い違い、前週の値を保存済みの重みで計算すること（AC-09）、AC-10 が実行環境のタイムゾーンに依存すること、削除の確認が編集中の目標名と照らし合わせること（AC-08）、境界の条件（空の本文、一覧に無い `sort`、`%` と `_`、小数第 2 位への丸め）など
- 事実の確認: 逆の期間でも作れる、`PUT` で期間を変えられる、`updated_at` が変わらない、キーワードの `,` と最後のページより先と数字でない `:id` が 500、目標が無いときと本文が空の `PUT` が 400、重みが小数第 2 位に丸められる、を、ローカルの Supabase で動かして確かめた
- クラウドの Supabase の `max_rows` の値は確かめていない（ローカルの設定は 1000）。週報の履歴の取得（`getGoalProgressHistories`）にも同じ心配があるかは、weekly-report の仕様を作るときに確かめる

## 対象外

- コードの修正（P5 ではコードを変えない。直すものは計画書の P6 に足す）
- 週報の「目標進捗状況」の組み立て（weekly-report の仕様）。週の境目と履歴の使い方は、この仕様の不変条件と落とし穴を参照する
