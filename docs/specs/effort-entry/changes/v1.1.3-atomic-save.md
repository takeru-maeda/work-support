# 工数の保存を「全部保存するか、何も保存しないか」にする

## 背景と目的

- 工数の登録（`POST /api/effort/entries`）と GAS からの取り込み（`POST /api/effort`）は、行ごとに Supabase へ書き込む。途中の行で失敗すると、それより前の行と作った案件・タスクが残る。画面は入力を残すので、送り直すと 2 重になる（effort-entry の既知の落とし穴、v1.0.7-baseline の人間の判断 1。effort-ingest-gas の人間の判断も同じ）
- MCP サーバーの `log_effort`（`docs/plans/active/mcp-server.md` の P2）は AI から呼ばれ、失敗すると送り直されやすい。その前提として、1 回の送信を 1 つのトランザクションにする
- あわせて、同じ保存の経路にあるバックログの不具合を直す
  - 実績・見積が 100 以上で、DB の桁あふれの 500 になる（画面も止めない。負の値も画面で止めない）
  - 1 回の送信の中だけ、大文字小文字だけが違う案件名・タスク名を最初のものにまとめる（DB の検索は区別するので扱いがそろっていない）
  - 同じ送信の中で使い回した `task_id` が、決めた案件のタスクかを確かめない
  - すべて保存したあとで候補の一覧（`projects_with_tasks_mv`）の作り直しに失敗すると、保存済みなのに 500 を返す（送り直すと 2 重になる）
- 成功の条件: どちらの経路でも、どの行で失敗しても `work_records`・`projects`・`tasks` に何も残らない。候補の作り直しの失敗は、保存の成功として返す

## 仕様の変更

effort-entry（`docs/specs/effort-entry/spec.md`）:

- 変更: **AC-effort-entry-02**: 旧「要素ごとに順に、案件を決める → タスクを決める → `work_records` に 1 行足す」→ 新「1 回の送信のすべての要素を、1 つのトランザクションで保存する（案件・タスクを決めて作り、`work_records` に 1 要素 1 行足す）。どこかで失敗したら、行も、作った案件・タスクも残さない。すべて成功したら `201 { saved: [...] }`（形は今と同じ）」
- 変更: **AC-effort-entry-03 / 04**: 旧「同じリクエストの中では、大文字小文字だけが違う名前を最初の案件・タスクにまとめる」→ 新「同じリクエストの中でも、DB と同じく大文字小文字を区別する」。`task_id` は、同じリクエストの中で使い回すときも、決めた案件のタスクであることを確かめる（違えば 400「指定したタスクが見つかりませんでした。」）
- 変更: **AC-effort-entry-05**: 実績と見積は、**小数第 2 位に丸めた値**が 0 以上 100 未満（DB の列 `numeric(4,2)` が丸めて保存するため。99.994 は 99.99 で保存でき、99.995 は 100.00 になるので 400）。外れたら、DB に触れる前に 400（「工数の時間は100未満を指定してください。」「見積工数は100未満を指定してください。」）。どの要素が誤りでも、何も保存しない
- 変更: **AC-effort-entry-07**: 旧「作り直しに失敗したら、行は保存済みのまま 500 を返す」→ 新「作り直しに失敗しても、保存の成功として 201 を返し、失敗は `error_logs` に残す（次に作り直すときに反映される）」
- 変更: **AC-effort-entry-17**: 送信前の検証に「実績・見積が負か、小数第 2 位に丸めて 100 以上の行は、その欄に『0 以上 100 未満』を出し、ほかの欠けと同じくトースト『入力内容を確認してください。』を出して止める」を足す（旧「負の値はここでは止めない」を廃止）。見積の欄にも、実績の欄と同じエラーの表示（文と枠の色）を付ける。AC-15 の「上限なし」は、数値の欄の矢印に上限が無いという意味に書き直す
- 不変条件の変更: **INV-2** に「作り直しに失敗しても保存は成功として返す。次に作り直すまで、作った案件・タスクは候補に出ない」を書き添える
- 不変条件の追加: **INV-5**: 1 回の送信の保存は、DB の関数 `save_work_records` の 1 回の呼び出しで行う（1 つのトランザクション）。破ると、途中の失敗で一部だけ残り、送り直しで 2 重になる

effort-ingest-gas（`docs/specs/effort-ingest-gas/spec.md`）:

- 変更: **AC-effort-ingest-gas-04**（保存）: 読めた行を、effort-entry と同じ DB の関数で 1 つのトランザクションに保存する。途中で失敗したら何も残さない（v1.1.2 で、書き間違いは DB に触れる前に 400 にしてある）
- 変更: **AC-effort-ingest-gas-05**: 候補の作り直しに失敗したときは、直後の `GET /api/projects` に新しい案件とタスクが出ない（次の作り直しで出る）、を但し書きに足す
- 変更（エラー時の挙動）: 「保存の途中の失敗: 500 で一部が残る」と「全行の保存のあとの作り直しの失敗: 500」を、「保存の関数の失敗: 500 で何も残らない」「作り直しの失敗: 201 で `error_logs` に残す」に書き換える
- 既知の落とし穴「途中の失敗で一部だけ残る」を消す。「送り直すと 2 重に登録される」（同じ送信を見分ける仕組みが無い）は残る

## 実装計画

- **手本にする既存コード**:
  - DB の関数を `rpc` で呼ぶ: `packages/api/src/features/effort/repository.ts:334`（`refreshProjectsWithTasksView`。エラーを `AppError(500)` に包む）
  - 関数の定義と権限: `packages/api/supabase/migrations/20261013010000_populate_projects_with_tasks_mv.sql` と、baseline の `refresh_projects_with_tasks_mv` の定義（`security definer` の有無、`search_path`、`grant`）
  - 結合テストの形: `packages/api/test/effort-entries.int.test.ts:137`（AC-02）
- **新しく作るファイル**: `packages/api/supabase/migrations/20261016000000_save_work_records.sql`
- **変更するファイル**: `effort/index.ts`（2 つのルートから service にロガーを渡す。作り直しの失敗を `error_logs` に残すため）、`effort/types.ts`、`packages/shared/supabase-gen-types.sh`、`effort/service.ts`（2 つの保存の関数を、検証 → `save_work_records` の 1 回の呼び出し → 候補の作り直し、にする）、`effort/repository.ts`（`saveWorkRecords` を足し、使わなくなった関数を消す）、`packages/shared/src/types/db.ts`（生成）、web の `formHelpers.ts`、`types.ts`、`TaskRow.tsx`
- **設計の方針**:
  - DB に触れない検証（名前が空、負、100 以上、要素が 0 件）は、今と同じく service で先に行い、1 つでも誤りがあれば何も呼ばずに 400
  - `save_work_records` は、要素ごとに案件を決める（`project_id` ならそのユーザーの案件か確かめる。名前なら `insert … on conflict (user_id, name) do nothing` のあとで探す）→ タスクを決める（`task_id` なら決めた案件のタスクか確かめる。名前なら同じく）→ `work_records` に挿入、を 1 つの関数の中で行う。見つからないときは決まったエラーコードの例外を投げ、service が 400 の文に変える。返り値は保存した行と「案件・タスクを新しく作ったか」
  - 関数は `security invoker`、`set search_path = ''`。baseline の既定の権限（`ALTER DEFAULT PRIVILEGES … GRANT ALL ON FUNCTIONS TO anon, authenticated`、baseline.sql:753-756）で anon と authenticated にも与えられてしまうので、`revoke execute … from public, anon, authenticated` のあとで `grant execute … to service_role` する（引数でユーザー ID を受け取るため、漏れると他人の工数を作れる）
  - 返り値は、入力の順に 1 要素 1 行の `entry_id, project_id, project_name, task_id, task_name, hours, estimated_hours`（丸めたあとの値）と、`project_created`、`task_created`。応答の `saved` と完了メールは、これをそのまま送信の順で使う（`project_id` / `task_id` で指定した要素の名前を、service で問い合わせ直さない）
  - 見つからないときの例外: 案件は `errcode` を決めた値（例: `WS001`）で「指定した案件が見つかりませんでした。」、タスクは（例: `WS002`）で「指定したタスクが見つかりませんでした。」。service が `code` で見分けて AppError(400) にする。ほかの DB の誤りは 500
  - service の保存の結果（`StructuredEffortSaveResult`）に、新しく作った案件名・タスク名の一覧を足す（応答の `saved` の形は変えない。MCP の `log_effort` が返す）
  - 候補の一覧の作り直しは、今と同じく保存のあとで別に呼ぶ（トランザクションの外）。失敗したら `error_logs` に残して 201 を返す
- **代替案とトレードオフ**:
  - 案 A（推奨）: DB の関数で 1 つのトランザクションにする。PostgREST はリクエストをまたぐトランザクションを持たないので、確実に全部か何もないかにできるのはこれだけ
  - 案 B: 失敗したら、それまでに入れた行を消して戻す（補償の処理）。消す途中でも失敗しうるうえ、同時の送信と競合する。採らない
- **確認したライブラリの使い方**: supabase-js 2.80 の `rpc(name, args)` は、関数の例外を `error`（`code` に SQLSTATE、`message` に例外の文）で返す（既存の `refreshProjectsWithTasksView` と同じ扱い）。実装の前に Context7 で `raise exception … using errcode` の受け取り方を確かめる

## テスト方針

- 結合（ローカルの Supabase）:
  - AC-02 / INV-5: 2 つ目の要素が他人の `task_id`（400）のとき、1 つ目の行も、1 つ目のために作った案件・タスクも残らない
  - AC-03 / 04: 1 回の送信の中で「ABC」と「abc」が別の案件になる（今の「既知の落とし穴」のテストを、先に Red に書き換える）。使い回した `task_id` が別の案件のものなら 400
  - AC-05: 実績 100、見積 100、99.995 で 400、99.994 で保存できる（99.99）。どの要素の誤りでも何も残らない
  - AC-07: 候補の作り直しが失敗しても 201 で、`logger.error` が呼ばれる（作り直しの `rpc` だけを失敗させる偽のクライアントで、service の単体テストとして確かめる）
  - 関数そのもの: `adminClient` から `save_work_records` を、2 つ目の要素を不正（他人の案件の ID）にして呼び、1 つ目の行も、1 つ目のために作った案件・タスクも残らない（GAS の経路は DB に触れる前の検証で誤りを止めるので、`POST /api/effort` を通しては関数の途中を失敗させられない）
  - effort-ingest-gas: 読めたすべての行を 1 回の `rpc('save_work_records')` で保存することを、`service.test.ts` の偽のクライアントで確かめる（INV-5）。候補の作り直しの失敗で 201 と `logger.error`
  - AC-04: 同じ送信の中の「Review」と「review」が別のタスクになる
  - 関数の権限: anon と authenticated のキーから `save_work_records` を呼べない（`browserClient` から `rpc` して拒まれる）
- 単体: service の、検証の誤りで DB に触れないこと（`service.test.ts` の、触れると失敗するクライアントの偽物を使う）
- 部品（web）: 送信前の検証で、負と 100 以上を止める
- 既存のテスト（AC-01〜11、ingest-gas のすべて）が、形を変えずに通ること。例外として書き換えるのは、`test/effort-entries.int.test.ts:226-237`（AC-03 の「最初の案件にまとめる」）と、web の `EffortForm.test.tsx:414`（「負の値はここでは止めない」）

- 完了メールの失敗を `error_logs` に残すこと、ほかの effort-entry のバックログの項目
