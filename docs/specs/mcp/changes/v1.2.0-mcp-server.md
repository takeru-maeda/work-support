# MCP サーバーを追加する

## 背景と目的

- Claude Code、Claude Desktop、Cursor、Notion AI から、自分の工数・目標・週報・ミッションを読み書きできるようにする（計画書 `docs/plans/active/mcp-server.md`。決定事項 D1〜D15 と、P1 で確かめた結果は計画書の決定ログにある）
- この記録は計画書の P4（土台と読むツール）、P5（書くツール）、P6（同意の画面とローカルでの通し）をまとめて扱う。**前提**: effort-entry v1.1.3（工数の保存を全部か何もないかに）と goals v1.2.0（期間をまとめて作る API）が先に終わっていること
- 成功の条件: ローカルの Supabase で、クライアントの自動登録 → 同意の画面 → トークン → `/mcp` のツールの呼び出しまでが E2E で通る。MCP 用のトークンでは `/api/*` を呼べない

## 仕様の変更

新しい機能 mcp の仕様書（`docs/specs/mcp/spec.md`）を作る。受け入れ基準:

**入口と認証**
- **AC-mcp-01**: `POST /mcp` は MCP の Streamable HTTP（状態を持たない。リクエストごとにサーバーを作る）で答える。`GET` / `DELETE /mcp` は SDK の既定の答え（405）。`Authorization: Bearer <Supabase のアクセストークン>` が無いか検証に失敗したら、SDK の形の 401（本文は OAuth の誤りの JSON）と `WWW-Authenticate: Bearer … resource_metadata="<API の origin>/.well-known/oauth-protected-resource/mcp"` を返す。この 401 は `error_logs` に残さない（アクセスログには残る）。API の origin は、リクエストの URL から取る
- **AC-mcp-02**: `GET /.well-known/oauth-protected-resource/mcp`（と `/.well-known/oauth-protected-resource`）は認証なしで `{ resource: "<API の origin>/mcp", authorization_servers: ["<SUPABASE_URL>/auth/v1"], bearer_methods_supported: ["header"] }` を返す
- **AC-mcp-03**: `/mcp` は、OAuth のクライアントに出したトークン（`client_id` の claim があるもの）も、web の画面のトークンも受け付ける（同じユーザーで権限も同じ。計画書の完成形で「P1 で決める」とした点の決定）。ツールはトークンのユーザーのデータだけを読み書きする
- **AC-platform-20**（platform に追加）: `jwtAuthMiddleware` を使うすべてのルート（`/api/*` の JWT のルート）は、`client_id` の claim があるトークンを 401 にする。テストはルートの一覧から作り、ルートを足しても漏れないようにする

**読むツール**（どれも `readOnlyHint: true`）
- **AC-mcp-04** `get_weekly_report { date? }`: `date`（YYYY-MM-DD）を含む週の週報を返す。省略すると**日本時間の今日**。本文は画面の週報（`GET /api/reports/weekly`）と同じ文字列で、ほかに工数のまとめと目標の進捗を構造化した値で返す。週の区切りは週報の仕様のまま（weekly-report の AC。日本時間にする直しはバックログ）
- **AC-mcp-05** `search_work_records { startDate, endDate, projectName?, taskName? }`: 期間（開始日と終了日を含み、366 日まで。超えたら誤り）の工数の行（日付、案件名、タスク名、見積、実績）を日付の昇順で返す。案件名・タスク名は大文字小文字を区別した完全一致で絞り、元の表（`projects`、`tasks`）を見る（候補の一覧のマテリアライズドビューは使わない。作り直しの失敗で新しい案件が見えないことがあるため）。`taskName` だけなら、その名前のタスクをすべての案件から探す。行は最大 500 行で、超えたら最初の 500 行と `truncated: true` を返す。実績・見積の合計と件数は、絞り込みに当たる**すべての行**について返す
- **AC-mcp-06** `list_projects {}`: 案件とその中のタスクの名前を、元の表から返す
- **AC-mcp-07** `get_goals { includePast? }`: 現在の期間（開始日はその期間の目標の開始日のいちばん早いもの、終了日）と、目標ごとの ID・名前・内容・重み・進捗率・前週からの差、全体進捗と加重進捗を返す。前週からの差は、目標の画面と同じ計算（`GET /api/goals/progress/previous-week`。履歴の無い目標は今の進捗率で数える。goals の AC-09、AC-10）。`includePast` なら過去の目標も期間ごとに返す
- **AC-mcp-08** `get_mission {}`: ミッションの本文を返す（無ければ空）

**書くツール**（`readOnlyHint: false`）
- **AC-mcp-09** `log_effort { date, entries: [{ projectName, taskName, estimatedHours?, hours }], memo? }`: 1 要素を `{ project_id: null, project_name, task_id: null, task_name, estimated_hours, hours }` に直し、effort-entry の保存（v1.1.3）で保存する。全部保存するか何も保存しない。成功したら保存した行と、新しく作った案件名・タスク名を返す。完了メールは画面の登録と同じ条件（メールアドレスがあり、設定で止めていない）で、応答のあとに送る。説明文に「失敗したときは `search_work_records` で保存されていないことを確かめてから送り直す」を書く
- **AC-mcp-10** `update_goal_progress { goalId, progress }`: 現在の期間の目標の進捗率だけを変え、履歴を残す（goals の INV-2）。現在の期間でない目標、他人の目標、無い目標は誤り（「現在の期間の目標が見つかりません。」）
- **AC-mcp-11** `update_mission { content }`: ミッションを書き換える。前後の空白を除いて空なら誤り（API の `PUT /api/missions` は空白だけも受け付けるが、AI からの誤った空の上書きを防ぐ）
- **AC-mcp-12** `create_goal_period { startDate, endDate, goals: [{ title, content, weight }], confirmToken? }`（`destructiveHint: true`）:
  - `confirmToken` が無ければ何も保存せず、goals の `validateGoalPeriod` の結果を返す: `errors`（誤りの文の一覧。無ければ空）、作られる期間と目標、`lockedGoals`（編集できなくなる今の目標の一覧）、`warning`（利用者に伝える文）、誤りが無ければ `confirmToken`
  - `warning` は、今の目標があれば「この期間を作ると、今の期間（yyyy/MM/dd〜yyyy/MM/dd）の目標 N 件は過去の目標になり、編集できなくなります。期間はあとから変えられません。」、無ければ「期間はあとから変えられません。」
  - `confirmToken` があれば、同じ入力と今の状態から作り直した値と一致し、かつ誤りが無いときだけ、goals の `createGoalPeriodService` で作る。誤りがあれば誤りを返して何も作らない。一致しなければ何も作らず「プレビューのあとに内容か状況が変わりました。もう一度プレビューしてください。」
  - `confirmToken` は、ユーザー ID、入力（期間と目標を正規化したもの）、今の期間の終了日と目標の ID の一覧から、Web Crypto（`crypto.subtle`）の SHA-256 で作る。秘密の値も期限も持たない（認可のためではなく、「このプレビューを見た」ことと「状況が変わっていない」ことを確かめるための値。状況が変われば一致しなくなるので、期限が無くても古いプレビューでは作れない）。**計画書の D10（署名つきの値）からの変更**
  - 説明文に「必ず 1 回目の結果の `warning` を利用者に見せ、同意を得てから `confirmToken` を付けて呼ぶ」と書く
- **AC-mcp-13**: どのツールも、業務の誤り（AppError の 400 など）は MCP のツールの誤り（`isError: true` と文）で返し、HTTP は 200 のまま。英語の誤りの文（goals の「Goal not found…」など）は、ツールの中で日本語に直す。想定外の誤りは「処理に失敗しました。時間を空けて再度お試しください。」で返し、`error_logs` に残す。ツールの入力の型の誤りは SDK の既定の答えのまま（テストでどちらの形かを固める）

**同意の画面（web）**
- **AC-mcp-14**: `/oauth/consent?authorization_id=…` は `AuthenticatedLayout`（`AuthGuard`）の外に置き、画面の中でセッションを確かめる。ログインしていなければ `/login?redirect=<元のパスとクエリ>` に移し、ログインのあとで戻す。ログインしていれば、Supabase から認可の内容を取り、クライアントの名前、戻り先、「このアプリが、あなたの工数・目標・週報・ミッションを読み書きできるようになります」を出して、「許可」「拒否」を選ばせる。許可・拒否のあとは、Supabase が返すクライアントの戻り先へ移る。すでに同意しているクライアントで、Supabase が認可の内容の代わりに戻り先を返したときは、そのまま戻り先へ移る。`authorization_id` が無いか無効なら「連携の情報が見つからないか、期限が切れています。連携するアプリからもう一度やり直してください。」を出す
- **AC-auth-13**（auth に追加）: `/login?redirect=…` は、ログインのあとで `redirect` に移る。`/` で始まり、`//` と `/\` で始まらない（このサイトの中の）パスだけを受け付け、それ以外はホームへ移す（外のサイトへ飛ばされないように）。新規登録の画面には引き継がない（新規登録のあとはホーム）
- 変更: **AC-auth-05**: 旧「ログインが成功したら `/` に移る」→ 新「`redirect` があれば AC-auth-13 に従い、無ければ `/`」。既知の落とし穴「ログインのあとに元の画面に戻らない」は、`/oauth/consent` からの移動だけが戻るようになったことに書き直す（`AuthGuard` が `/landing` に移す保護された画面は今のまま）
- 変更: **AC-auth-01**: ルートの一覧に `/oauth/consent`（ログインしていなくても開け、画面の中でログインへ移す）を足す
- 変更: **auth の INV-1** に例外を足す: `/oauth/consent` は `AuthGuard` の外に置き、自分でセッションを確かめる（未ログインのときの行き先を `/landing` ではなく `/login?redirect=` にするため）。ユーザーのデータは表示しない
- 変更: **auth の INV-4**（ローカルの戻り先）: ローカルの `site_url` を `http://localhost:5183`（`pnpm dev:local` と E2E の web）にし、`additional_redirect_urls` に足す
- 変更: **AC-platform-08**: ルートの一覧に `/mcp`、`/.well-known/oauth-protected-resource`（と `/mcp` の付いたもの）を足す
- 変更: **platform の INV-4**（誤りの応答の形）の例外に足す: `/mcp` の 401 は SDK の形で `error_logs` に残さない。ツールの誤りは HTTP 200 の MCP の結果で返す

**不変条件**
- **INV-mcp-1**: ツールは HTTP を経由せず、各機能の service を呼ぶ。入力の検証、ユーザーの絞り込み、保存のトランザクションは service と DB の関数の決まりをそのまま使う。ツールの層（`features/mcp/tools/`）は入出力の変換だけを行い、業務の判断を書かない。破ると、画面と MCP で振る舞いがずれる
- **INV-mcp-2**: OAuth のクライアントのトークンは、この API では `/mcp` だけで受け付ける（AC-platform-20）。破ると、MCP 用に渡したトークンでアカウントの削除まで呼べる。Supabase を直接呼ぶ使い方（Storage、Auth）は、この API の外なので別に扱う（下の「人間に判断してほしい点」）
- **INV-mcp-3**: 取り消せない操作（アカウントの削除、目標の削除）はツールにしない

- **設計の方針**:
  - `/mcp` のルートで、SDK の `requireBearerAuth` で検証し、`createMcpHandler` の `fetch(c.req.raw, { authInfo })` に渡す。verifier は今の `verifySupabaseAccessToken` を包み、`AuthInfo` に `clientId`（無ければ `"web"`）、`expiresAt`（JWT の `exp`）、`extra.user`（`buildAuthenticatedUserFromPayload` の結果。ユーザー ID とメールアドレス）を入れる。ルートでも `c.set("user", …)` して、アクセスログに `user_id` を残す
  - ツールは `authInfo.extra.user` からユーザーを取り、`c.env` から作った Supabase のクライアントで service を呼ぶ。`log_effort` の完了メールは、ルートの `c.executionCtx.waitUntil` とロガー、`accessLogId` を factory に渡して、画面の登録と同じ関数で送る
  - ツールの結果は、人が読める日本語の本文（`content` の text）と、構造化した値（`structuredContent` と `outputSchema`）の両方で返す
  - テストは `callApi` から JSON-RPC を直接送る（MCP のクライアントの SDK は足さない。計画書の D14 の「SDK のクライアントから」を変える）
  - ブラウザから直接 `/mcp` を呼ぶクライアントは対象外にする（CORS の許可するヘッダーは変えない）
- **代替案とトレードオフ**:
  - `confirmToken` を署名（HMAC）と期限つきにするか: 秘密の値が要り、Workers のシークレットの追加（人の操作）が増える。目的は「プレビューを見た」ことと「状況が変わっていない」ことの確認で、状態に結び付けたハッシュで足りる。AI がハッシュを自分で計算して 1 回目を飛ばすのは現実的でなく、飛ばしてもサーバーの確認（goals の AC-23）は必ず通る
- **確認したライブラリの使い方**: `@modelcontextprotocol/server` 2.3.0。`createMcpHandler(factory)` が返すハンドラーの `fetch(request, { authInfo })`。ツールの中では、factory の引数で `authInfo` を受け取る。`registerTool(name, { description, inputSchema: z.object(...), annotations }, handler)`。Zod 4.6.5 の `.describe()` が JSON Schema に載る。`initialize` なしでも `tools/list` に答える（P1 で確かめた）。`requireBearerAuth` は `AuthInfo.expiresAt` が無いトークンを拒む。`AuthInfo.extra` に任意の値を入れられる。supabase-js 2.80 の `auth.oauth.getAuthorizationDetails`、`approveAuthorization`、`denyAuthorization`（P1 で確かめた）

## UI の方針

- 手本の画面: ログインの画面（`/login`）。カードの中に、ロゴ、見出し「アプリの連携を許可しますか？」、クライアントの名前、戻り先の URL（小さく）、許可される内容、「拒否」（outline）と「許可」（primary）のボタン。読み込み中は Skeleton、誤りは文と「ホームへ」のリンク
- 流用する部品: shadcn の `Card`、`Button`、`Skeleton`、ログインの画面のレイアウト
- レスポンシブの方針: 375px ではカードを全幅にし、ボタンを縦に並べる。768 / 1280px はログインの画面と同じ幅
- 今の画面の確認結果: 実装の前に、Playwright MCP でログインの画面を見る

## テスト方針

## 人間に判断してほしい点

- **MCP 用のトークンで、Supabase を直接呼べること**: OAuth のトークンは、ふつうのログインと同じ `authenticated` のトークン。この API の外で、ブラウザと同じように Supabase を直接呼べる。具体的には、アバターの Storage（自分のフォルダへの書き込み・削除）と、Auth の自分のユーザーの情報の読み書き（メールアドレスやパスワードの変更を含む可能性）
  - 案 A（推奨）: Storage のポリシーに `client_id` が無いことの条件を足す（小さなマイグレーション）。Auth のほうは Supabase の側の仕組みで、この改修では防げないので、リスクとして仕様書に書く。トークンを渡すのは自分が使うアプリだけで、トークンは 1 時間で切れる
  - 案 B: どちらもリスクとして書くだけにする
  - 実装の最初に、ローカルの Supabase で、OAuth のトークンで Storage と `/auth/v1/user` を実際に呼べるかを確かめ、結果を記録に書く
  - **人間の判断（2026-10-16）: 案 A**（Storage のポリシーに `client_id` が無いことの条件を足す。Auth はリスクとして仕様書に書く）
- **`confirmToken` の作り（計画書の D10 の変更）**: 署名つき・期限つきから、秘密の値も期限も持たないハッシュに変える（理由は「代替案とトレードオフ」）
