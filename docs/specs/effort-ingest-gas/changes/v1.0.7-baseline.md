## 照合の結果

| 項目 | 旧ドキュメント | コード | 扱い |
| --- | --- | --- | --- |
| 実績が空のとき | `null`（`08-logic.md`「解析ルール」） | 0 として保存（`insertWorkRecord` の `effort.hours \|\| 0`。`hours` の列は NULL 不可） | コードを正とした（AC-06）。**要確認 1** |
| タスクの行の正規表現 | `^・(.+?)：\[(.*?)\]<(.*?)>`（行末の指定なし） | 同じ形に行末（`$`）が付き、行の前後の空白を除いてから照合する | コードを正とした。`<実績>` のあとに文字があると、旧ドキュメントでは読め、コードでは読み飛ばす |

### 要確認

1. **実績が空のときに 0 で保存するのは意図どおりか**: 旧ドキュメントは `null` だが、`hours` の列が NULL 不可なので 0 にしている。週報や工数一覧で「実績 0」と「未入力」は区別しなくてよいか。推奨: 今のまま（0）とし、旧ドキュメントの記述を誤りとする
2. **書式に合わない行を黙って読み飛ばしてよいか**: 書き間違えた行だけが登録されず、利用者は気づけない。推奨: 読み飛ばした行があれば 400 にして、GAS の開発者向けメールで気づけるようにする（挙動の変更なので、改修の記録を通して P6 以降に行う）
3. **途中で失敗したときに、一部だけ保存されてよいか**: 送り直すと 2 重になる。推奨: 1 回の送信をまとめて保存する（DB の関数かトランザクションにする）改修を P6 以降に行う
4. **大文字小文字だけが違う案件名・タスク名が 1 回の送信に混ざったとき**: 2 つ目以降が最初のものに付く。別々の送信なら別の案件・タスクになり、扱いがそろっていない。推奨: 解析の中のキャッシュも大文字小文字を区別するように直す（小さい不具合として P6 で直す）
5. **負の値や数値として読めない値を通してよいか**: Web の工数登録は負の値を 400 にしているが、この経路は通す。`1,5` は黙って 1 になる。推奨: 書式に合わない行と同じ扱い（要確認 2）にそろえる
6. **Auth の障害を 400 `User not found` にしてよいか**: GAS から届くメールで、障害とメールアドレスの誤りを区別できない。推奨: ユーザーの検索の失敗は 500 にする（小さい修正として P6 で直す）

### 人間の判断（2026-10-14）

| # | 判断 |
| --- | --- |
| 1 | 今のまま（実績が空なら 0）。旧ドキュメントの `null` の記述は誤りとする |
| 2、5 | 書式や数値の書き間違いは 400 にして、何も保存しない（P6 以降に改修の記録を通して直す） |
| 3 | 1 回の送信を、全部保存するか全部保存しないかにする（P6 以降に改修の記録を通して直す） |
| 4、6 | どちらも P6 で直す（大文字小文字の扱いをそろえる。Auth の障害は 500 にする） |

## 仕様レビュー（spec-reviewer）

- Major 4 件（大文字小文字はタスクにも当てはまる、数値の扱いは断定できる、Auth の障害でも 400、ビューの更新と失敗の関係）と Minor 6 件を受けて、spec.md を直した
- レビューで「要確認」とされた 3 点は、ローカルの Supabase で確かめてから書いた: 末尾に `/` を付けたパスは 401、`Content-Type` が JSON でないときはユーザーの検索のあとで検証ライブラリの既定の形の 400、`GET /api/projects` はマテリアライズドビューを読む
