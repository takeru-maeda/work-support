# GAS からの取り込みで、書き間違いを 400 にして何も保存しない

## 背景と目的

- Google Form から送った工数のテキストは、書式に合わない行を**黙って読み飛ばし**、数値の書き間違いも黙って通している（`1,5` は 1、`abc` は実績 0、負の値もそのまま）。利用者にはエラーが届かず、一部の行だけが登録されないことに気づけない（spec.md の「既知の落とし穴」）
- 1 回の送信の中で大文字小文字だけが違う名前（案件 `ABC` と `abc`）を、最初の案件にまとめてしまう。別々の送信なら別の案件になるので、送り方で結果が変わる
- ユーザーの検索で Auth の管理 API が失敗したとき（Supabase の障害）も 400「User not found」を返し、送り手の誤りと区別できない
- P5 の人間の判断（[v1.0.7-baseline](v1.0.7-baseline.md) の 2、4、5、6）と、2026-10-15 の追加の判断（下の「確認したこと」）に従って直す
- **成功の条件**: 書式・数値の誤りが 1 つでもあれば、1 行も保存せずに 400 を返し、どの行が何で読めなかったかがメッセージでわかる。正しい書式の送信は今までどおり保存される。1 回の送信の中でも大文字小文字を区別する。Auth の障害は 500

### 確認したこと（2026-10-15、人間の判断）

| # | 問い | 判断 |
| --- | --- | --- |
| 1 | `■` でも `・` でも始まらない、空白以外の文字がある行 | 400 にする（メモの行も送れなくなる） |
| 2 | 全角の数字（`２．５`） | 半角に直して受け付ける |

## 仕様の変更

- 変更: **AC-effort-ingest-gas-05**: 旧「1 回の送信の中では、大文字小文字だけが違う名前は最初に出てきたものにまとめる」→ 新「1 回の送信の中でも、名前の比較は大文字小文字を区別する（DB の検索と同じ）。`ABC` と `abc` は別の案件、同じ案件の下の `Review` と `review` は別のタスクになる」
- 変更: **AC-effort-ingest-gas-06**: 旧「`Number.parseFloat` で読む。読めなければ見積なし / 実績 0。先頭が数値なら後ろを捨てる。負の値もそのまま」→ 新「見積と実績は、前後の空白を除き、全角の数字と全角のピリオド（`０`〜`９`、`．`）を半角に直したうえで、空か、`/^\d+(\.\d{1,2})?$/` に合い 100 未満の値（例: `2`、`1.5`、`0.25`、`99.99`）。小数を第 2 位までに限るのは、DB の列（`numeric(4,2)`）が丸めて `99.995` を 100.00 にし、桁あふれの 500 になるため。見積が空なら見積なし（NULL）、実績が空なら 0（P5 の判断 1。今のまま）。それ以外（`1,5`、`1.5h`、`abc`、`-1`、`.5`、`100`、`99.995`、`1.2.3`）はその行の誤り」
- 変更: **AC-effort-ingest-gas-07**: 旧「次の行は読み飛ばし、エラーにしない …。読めたタスクの行が 1 つも無いときは 400」→ 新「空の行（空白だけの行を含む）は読み飛ばす。それ以外で次のどれかに当たる行があれば、**1 行も保存せずに** 400 を返す: `■` でも `・` でも始まらない行、名前が空の案件の行（`■` だけ）、最初の案件の行より前のタスクの行、`・<タスク名>：[<見積>]<実績>` の形でないタスクの行（`：` が半角、括弧が全角か欠けている、`>` のあとに文字がある、など）、名前が空のタスクの行、数値が AC-06 に合わない行。メッセージは「工数のテキストに読めない行があります。」+ 半角空白 + 誤りのある行ごとの「`<行番号>行目: <理由>`」を ` / ` でつないだもの（件数の上限は無い。例: `工数のテキストに読めない行があります。 3行目: タスクの行の書式が正しくありません / 5行目: 実績は 0 以上 100 未満の、小数第 2 位までの数値にしてください`）。行番号は送られたテキストの 1 始まりの行。**理由は 1 行に 1 つ**で、次の順に最初に当たったものを出す: (1) `■` でも `・` でも始まらない →「案件の行（■）でもタスクの行（・）でもありません」、(2) `■` の後ろが空 →「案件名がありません」、(3) 最初の正しい案件の行より前のタスクの行 →「最初の案件の行より前にタスクの行があります」、(4) `・<タスク名>：[<見積>]<実績>` の形でない →「タスクの行の書式が正しくありません」、(5) タスク名が空か空白だけ（`・：[1]<2>` も含む）→「タスク名がありません」、(6) 見積が AC-06 に合わない →「見積は 0 以上 100 未満の、小数第 2 位までの数値にしてください」、(7) 実績が合わない →「実績は 0 以上 100 未満の、小数第 2 位までの数値にしてください」。名前が空の案件の行（`■` だけ）の後ろ、次の正しい案件の行までのタスクの行は、(3) として別に報告しない（`■` だけの行の誤りだけを出す。書式の誤りは (4)〜(7) で報告する）。誤りが無く、タスクの行が 1 つも無いときは、今までどおり 400「工数の値が不正です。登録件数が0件でした。」」
- 変更（エラー時の挙動）: 旧「ユーザーの検索で Auth の管理 API が失敗したときも 400 `User not found`」→ 新「Auth の管理 API が失敗したときは 500 `Failed to look up user`（原因は `error_logs` に残る）。見つからないときは今までどおり 400 `User not found`」
- 不変条件の変更: **INV-4**: 旧「黙って変えると、それまでの書き方の行がすべて読み飛ばされる」→ 新「黙って変えると、それまでの書き方の送信がすべて 400 になり、1 行も登録されない（GAS が開発者にメールを送るだけで、利用者には届かない）」。書式を変えるときに案内と GAS の更新を合わせて行う点は変えない。**この改修も、利用者から見ると書式の変更（メモの行、`■` だけの行、数値の書き方が 400 になる）なので、本番に反映する前に、人間が Google Form の説明文に書式を明記する**（リリースの条件。下の「対象外」）
- 不変条件の追加:
  - **INV-5**: テキストは、保存を始める前に全部を読み、誤りが 1 つでもあれば DB に触れずに 400 を返す（読みながら保存しない）。破ると、書き間違いのある送信で前半の行だけが保存され、直して送り直すと 2 重になる。なお、読み終えたあとの保存の途中で DB が失敗したときに一部が残る点は、この改修では直さない（対象外）

## 実装計画

- **手本にする既存コード**:
  - `packages/api/src/middleware/auth.ts:66-75`: 検証の誤りを集めて ` | ` でつなぎ、`AppError(400, ...)` で投げる形。行ごとの誤りの集め方とメッセージの作り方を踏襲する（区切りは行の中の「 | 」と紛れないよう ` / ` にする）
  - `packages/api/src/features/effort/service.ts:474-497`（`parseTaskText`）: 1 行を正規表現で読む純粋関数。これを「読めた結果か、誤りの理由」を返す形に変える
- **変更するファイル**:
  - `packages/api/src/features/effort/service.ts`: `parseEffortText` を `{ efforts, errors }`（`errors` は `{ line: number; reason: string }[]`）を返す形にし、`saveEffortRecords` は `errors` があれば DB に触れる前に `AppError(400)` を投げる。数値は `parseHours`（全角を半角に直し、`/^\d+(\.\d{1,2})?$/` と 100 未満を確かめる）で読む。案件とタスクのキャッシュのキーから `toLowerCase()` を外す（GAS の経路の中だけ）
  - `packages/api/src/features/effort/types.ts`: 読んだ結果の型（`ParsedEffortText`、`EffortTextError`）を足す
  - `packages/api/src/middleware/auth.ts`: `findUserByEmail` の `error` があれば `AppError(500, "Failed to look up user", error)`、ユーザーが無ければ今までどおり 400
- **設計の方針**: 読む（純粋関数、DB なし）→ 誤りがあれば 400 → 保存、の順にし、読む処理は単体テストで細かく確かめる。理由の文言と判定の順番は AC-07 のとおり（1 行に 1 つ）。タスクの行の正規表現は、タスク名が空でも形として読めるように `(.+?)` を `(.*?)` にし、名前の空は (5) で判定する
- **代替案とトレードオフ**:
  - 誤りの行だけ捨てて残りを保存する案: 今の「黙って一部だけ登録」と同じ問題が残るので採らない（P5 の判断 2、5）
  - 上限を 100 未満にする理由: DB の列が `numeric(4,2)`（99.99 まで）で、100 以上は保存の途中で 500 になり一部が残る。読む段階で止める
- **確認したライブラリの使い方**: 使わない（正規表現と文字列の置き換えだけ）
