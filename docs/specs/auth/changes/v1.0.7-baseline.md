# 移行時点の基準（認証）

## 背景と目的

- ハーネス移行計画の P5 で、旧要件定義書・旧詳細設計書（`docs/legacy/specs/`）と、v1.0.7 時点のコードを照らし合わせて `spec.md` を作った。この記録は、その時点の姿の基準と、照合で見つかった食い違いを残すもの
- 範囲は web の認証の画面と、保護された画面の扱い。API のトークンの検証は platform の仕様
- 食い違いはコードを正とした。意図かどうかを判断できないものは「要確認」として人間に聞く

### 要確認

1. **ログインしたまま `/login`・`/signup`・ランディングページを開いたら、ホームに移すか**: 今はそのまま表示し、ログインの画面からもう一度ログインできる。存在しないパスも、ログインしていても `/landing`（宣伝のページ）に移る。旧ドキュメントはホームに移すとしていた。推奨: ログイン済みならホームに移す。存在しないパスは、ログイン済みならホーム、未ログインならランディングにする（P6 以降に改修の記録を通す）
2. **ログアウトでほかの端末もログアウトさせてよいか**: 今の `signOut()` は既定の global で、ヘッダーのログアウト、パスワードの再設定の成功、「メールアドレスを変更」のどれでも、ほかの端末のセッションが終わる。推奨: ヘッダーのログアウトはこの端末だけ（`scope: 'local'`）にする。パスワードの再設定の成功のときは、ほかの端末も終わらせる今のまま（パスワードが漏れたときのため）

### 見つけた不具合（計画書の P6 に足すもの）

- 認証の状態の変化を聞いておらず、別のタブでのログアウトや 401 に気づかない
- ユーザーの確かめが通信の失敗でも未ログインとして扱われ、`/landing` に移される
- 保護された画面を移るたびに、ユーザーの確かめと設定の取得をやり直す
- ログインのあとに元の画面に戻らない
- 新規登録のトーストが、メールの確認が要らない設定でも出る。確認が要る設定では説明なく `/landing` に戻る
- 再設定のあとに `/login?reset=success` の案内を出していない
- 再設定のリンクの読み取りが supabase-js と競合しうる（`PASSWORD_RECOVERY` のイベントを使う）
- ログイン・新規登録・再設定のエラーの文が英語のまま。`error_logs` にも残らない
- ログアウトで SWR のキャッシュと設定のストアを消さない。ログアウトの失敗を知らせない
- 別のタブでアカウントが替わると、ストアのユーザー ID とトークンの持ち主がずれ、別人のデータが混ざる（`onAuthStateChange` で受けてストアと SWR を消す）
- ローカルの Supabase の設定に、再設定のリンクの戻り先（web の `/reset-password`）が入っていない

## 仕様レビュー（spec-reviewer）

- Major 4 件、Minor 7 件を受けて spec.md と記録を直した。Major は、別のタブでアカウントが替わると別人のデータが混ざる経路（INV-2 の守れる範囲を限った）、設定のストアがキーを持たず前のユーザーの値が見えうること、再設定のリンクの戻り先がローカルの設定に無いこと（INV-4）、ログアウトがほかの端末も終わらせること（要確認 2）。Minor は、再設定のリンクを開いた時点でログインした状態になること、新規登録の 6 文字の検査がブラウザで先に止まること、読み込み中の表示は最初だけのこと、再設定の異常系、セッションの取得の失敗、テストとの対応、アカウントの削除のあとのログアウト
- 事実の確認: ログイン済みでも `/login` が出ること、存在しないパスが `/landing` に移ること、画面を移るたびに確かめをやり直すことを `pnpm dev:local` で確かめた

## 対象外

- コードの修正（P5 ではコードを変えない。直すものは計画書の P6 に足す）
- API のトークンの検証（platform）、アカウントの削除（profile）、ランディングページの中身（landing）、ヘッダー（app-shell）
