# ミッション

## TL;DR・改修前の必読

- 利用者ごとに 1 つの自由記述のミッション（業務の中長期的な指針）を持ち、週報の画面（`/weekly-report`）の上の欄で表示・編集する
- 週報の本文には入らない。利用者は週報とは別に、この欄の内容を貼る（weekly-report の人間の判断 3）
- ⚠️ 保存は「最後に保存したものが勝つ」。端末どうしの競合の制御は無い（[§既知の落とし穴](#既知の落とし穴)）

## 目的と利用者

- 目的: 週報に毎週書くミッションを 1 か所に保ち、必要なときに書き直す
- 利用者と使う場面: 期の初めや方針が変わったときに書き直し、週報を書くときに読んで貼る

## 振る舞いと受け入れ基準

### API（`/api/missions`、JWT）

- **AC-missions-01**: `GET` は、そのユーザーのミッションがあれば `200 { mission: { id, user_id, content, updated_at } }`、無ければ `200 { mission: null }`。トークンが無ければ 401
- **AC-missions-02**: `PUT { content }` は、ミッションがあれば内容と `updated_at`（サーバーの現在時刻）を上書きし、無ければ作る。どちらも `200 { mission }` を返す。`content` は 1 文字以上の文字列（空文字や無しは 400。上限は無い）。前後の空白は除かず、空白だけでも受け付ける
- **AC-missions-03**: どちらの操作も、トークンのユーザーのミッションだけを読み書きする。ミッションはユーザーごとに 1 件（`user_id` が一意）

### 画面（`/weekly-report` の「ミッション」）

- **AC-missions-04**: 取得中は 3 行の読み込み中の表示を出す。取得できたら内容を改行を残して表示する（連続する空白と行頭の空白は 1 つにまとまる）。ミッションが無い（または内容が NULL）なら「まだミッションが設定されていません。」を出す
- **AC-missions-05**: 「編集」を押すと、今の内容を入れた入力欄（「ミッションを入力してください...」）と「キャンセル」「保存」を出す。「保存」は、前後の空白を除いた内容が空のとき、保存中、保存済みの内容と同じとき（保存済みの側は空白を除かずに比べる）は押せない。「キャンセル」は保存中も押せ、その時点で取得している最新の内容に戻して閉じる
- **AC-missions-06**: 「保存」を押すと、前後の空白を除いた内容で `PUT` を送り、待っている間はボタンを「保存中...」にし、ページの見出しの横に「保存中...」のスピナーを出す（入力欄は操作できるまま）。成功したら「ミッションを更新しました」を出して編集を閉じ、表示をすぐ新しい内容にする（取り直さない）。失敗したら「ミッションの更新に失敗しました」を出し、編集中の内容を残す（`error_logs` に送る）
- **AC-missions-07**: 取得に失敗したら、「編集」の代わりにエラーの文と「再読み込み」を出す。「再読み込み」で取り直す。編集中でも、取得の失敗はエラーの表示を優先し、入力欄を隠す（入力は画面の中に残り、取り直しが成功すると戻る）

## 画面と API

### 画面
- ルート: `/weekly-report`（週報出力）の上半分。画面全体と下半分の週報は weekly-report の仕様
- 主な操作: 「編集」→ 入力 →「保存」/「キャンセル」

### API
| メソッドとパス | 認証 | 入力 | 出力 | 主なエラー |
| --- | --- | --- | --- | --- |
| `GET /api/missions` | JWT | なし | `GetMissionResponseSchema` | 401、500 |
| `PUT /api/missions` | JWT | `UpdateMissionRequestSchema` | `UpdateMissionResponseSchema` | 400、401、500 |

スキーマは `packages/shared/src/schemas/missions.ts`。全エンドポイントは [docs/reference/api.md](../../reference/api.md)。

## データ

- [missions](../../reference/database.md#missions): ユーザーごとに 1 行（`user_id` が一意）。`content` は NULL を許す（API からは NULL を書けない）。`updated_at` は保存のたびにサーバーの時刻で更新する
- アカウントを消すと、ミッションも一緒に消える（外部キーの CASCADE。アカウントの削除は profile の仕様）
- 画面: SWR のキー `/api/missions_<ユーザー ID>`。入力中の内容は部品の状態だけに持つ。保存の成功のあとは応答の内容でキャッシュを書き換え、取り直さない

## 設計不変条件

- **INV-1**: ミッションはユーザーごとに 1 件。`PUT` は「更新して、無ければ作る」。破ると（`user_id` の一意の制約を外す、作るだけにする）、`GET` が複数行で失敗し、画面に出せなくなる
- **INV-2**: どのクエリも、トークンのユーザーの `user_id` で絞る（service role で接続しているので RLS に守られない）。破ると、他人のミッションを読み書きできる

## エラー時の挙動

- 取得の失敗: 画面に axios のエラーの文（英語のことが多い。例: `Request failed with status code 500`）と「再読み込み」。トーストは出さない
- 保存の失敗: 「ミッションの更新に失敗しました」のトーストと `error_logs`。編集中の内容は残る
- API の入力の検証の失敗は 400（`{ data, error: [...], success: false }` の形）、DB の失敗は 500

## 既知の落とし穴

- **端末どうしの競合の制御が無い**: 最後に保存したものが勝つ（人間の判断 2 で、仕様とする）。別の端末で古い内容を開いたまま編集して保存すると、新しい内容を上書きする。編集中は、画面にフォーカスが戻って取り直しても、入力欄の内容は変わらない
- **入力が失われる経路**: 入力は画面の中（部品の状態）にしか無く、下書きの保存もページを離れるときの確認も無い。次の場合に消える
  - 画面を移る、再読み込みする、タブを閉じる
  - 保存中に「キャンセル」を押し、その保存が失敗する（失敗のトーストは出るが、編集は閉じていて入力は戻らない）
  - 保存中に打ち足した文字（送るのは押した時点の内容で、成功すると編集を閉じる）
  - 編集中に、フォーカスが戻ったときの取り直しが失敗すると、入力欄がエラーの表示に置き換わる。取り直しが成功すれば戻るが、利用者には消えたように見え、そこで再読み込みすると本当に失われる

  保存中と取り直しの失敗の 2 つは P6 で直す予定。画面を離れたときに消えるのは仕様とする（[v1.0.7-baseline](changes/v1.0.7-baseline.md) の人間の判断 1）
- **初めての保存を同時に 2 回送ると、片方が 500**: 「更新して、無ければ作る」を 2 つの問い合わせで行うので、まだミッションが無いユーザーが同時に 2 回保存すると、両方が「無い」と判断して作ろうとし、片方が一意の制約で失敗する（ローカルの Supabase で確かめた）。画面は保存中にボタンを押せないので、同じ画面からは起きにくい。P6 で直す予定
- **空白だけの内容**: 画面は前後の空白を除いて送り、空なら押せないが、API は空白だけの内容も保存する
- **取得の失敗の文が英語のまま**: エラーの文をそのまま出す。P6 で直す予定
- **内容が NULL の行**: 表示は「まだミッションが設定されていません。」になるが、文字の色は設定済みの色になる（API からは NULL を作れないので、手で DB を触ったときだけ）
