# 移行時点の基準（基盤）

## 背景と目的

- ハーネス移行計画の P5 で、旧要件定義書・旧詳細設計書（`docs/legacy/specs/`）と、v1.0.7 時点のコードを照らし合わせて `spec.md` の残りの節（リクエストの流れ、ログ、エラー処理、CORS、OpenAPI、画面からのエラーの記録、メールの依頼）を埋めた。この記録は、その時点の姿の基準と、照合で見つかった食い違いを残すもの
- API の認証（JWT）は、先に v1.1.0 で作った節（AC-platform-01〜07、INV-1〜3）。番号はそのまま残した。GAS の API キーの認証は effort-ingest-gas の仕様
- 食い違いはコードを正とした。意図かどうかを判断できないものは「要確認」として人間に聞く

### 要確認

1. **OpenAPI の定義と Swagger UI を、本番で誰でも開けてよいか**: 今は `GET /openapi` と `GET /ui` が認証なしで、GAS の取り込みを含む全ルートの入出力が見える。推奨: 本番では出さない（開発用とローカルだけにする）。API の一覧は `docs/reference/api.md` にあるので困らない
2. **CRITICAL のエラーのメールを作るか**: 旧要件にあったが実装されていない。今は CRITICAL を出す処理も無い。推奨: 今は作らず、要件から外す（必要になったら改修の記録を通して作る）

### 見つけた不具合（計画書の P6 に足すもの）

- DB のエラーの文がそのまま利用者への応答に出る（一般的な文にし、元の文は `error_logs` にだけ残す）
- 壊れた JSON の本文などの Hono の例外が 500 と ERROR の記録になる（400 にする）
- 予期しない例外の本当のメッセージが `error_logs.message` に残らない
- 入力の検証の失敗と 404 が `accessLogId` を返さず、`error_logs` にも残らない
- ルートで例外が出たとき、アクセスログの更新が 2 回走る
- `shared/src/schemas/logs.ts` の JSDoc のパスが `POST /api/logs`（実際は `/api/logs/error`）
- アクセスログが書けないと全部止まり、CORS のヘッダーの無い応答になる
- 401 のたびに `access_logs` と `error_logs` に書き、消す仕組みが無い
- 開発用の Origin（`http://localhost:5173`）が本番でも許可される
- エラーの記録の API に、大きさと回数の上限が無い。`source` と `level` を利用者が決められる
- 画面のエラーの送信（`reportUiError`）が失敗を投げる。画面全体のエラーの受け止めが無い（app-shell）
- `x-app-version` が送られず、API のエラーにアプリのバージョンが入らない
- 使っていない環境変数（`DEVELOPER_EMAIL`、`APP_EMAIL`、`GOOGLE_*`）
- （直した）steering の `api-standards.md` と `error-handling.md` が `accessLogId` を uuid と書いていた（実際は数値）。P5 の中で文書だけ直した

## 仕様レビュー（spec-reviewer）

- Major 2 件、Minor 7 件を受けて spec.md と記録を直した。Major は、INV-4（エラーの応答の形）が検証の失敗と 404 という今の例外と食い違っていたこと（範囲を `globalErrorHandler` を通るエラーに絞り、例外を書いた）と、AC-08 の「存在しないパスは 401」がトークンの無いときだけの話だったこと。Minor は、アクセスログの更新が 2 回走ること、エラーの記録が応答のあとで失敗しても捨てられること、メールの失敗の判定、`reportUiError` のメッセージの決め方、アクセスログが書けないときの応答、テストとの対応の分け方、AC-11 の「応答のスキーマ」の意味
- 事実の確認: 壊れた JSON が 500、許可していない Origin にも処理をして `Access-Control-Allow-Origin` を付けないこと、`localhost:5173` が許可されること、存在しないパスの 404 と機能の下の 401、`/openapi` が認証なしで開けることを、ローカルで確かめた
