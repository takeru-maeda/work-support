# API の認証を公開鍵方式（JWKS）のアクセストークンにも対応させる

## 背景と目的

- API の認証（`jwtAuthMiddleware`）は、Supabase の**共有シークレット方式（HS256、`SUPABASE_JWT_SECRET`）**で署名されたアクセストークンしか検証できない
- ローカルの Supabase（CLI 2.120）は、アクセストークンを**公開鍵方式（ES256）**で署名し、HS256 に戻す設定が無い（`supabase gen signing-key` も ES256 / RS256 だけ）。そのため、ハーネス移行計画の P4 で作るローカルの結合テストと E2E で、ログインしたユーザーが API を呼ぶと 401 になる
- Supabase は公開鍵方式への移行を勧めており、HS256 は「本番では推奨しない」としている。本番のプロジェクトで署名の鍵を切り替えると、今の API は全員のリクエストを 401 で拒否する
- **成功の条件**: 共有シークレット方式のトークン（今の本番と開発用）は今までどおり通り、公開鍵方式のトークン（ローカル、将来の本番）も、そのプロジェクトが公開する鍵（JWKS）で検証して通る。それ以外は 401

`platform` 機能の `spec.md` はまだ無い。工程 7 で、この改修の範囲（認証）を中心に新しく作る。

## 仕様の変更

- 追加: **AC-platform-01**: `SUPABASE_JWT_SECRET` で HS256 署名された有効なアクセストークンは認証が通り、`sub` がユーザー ID、`email` がメールアドレスになる（今までと同じ）
- 追加: **AC-platform-02**: そのプロジェクトの JWKS（`<SUPABASE_URL>/auth/v1/.well-known/jwks.json`。`SUPABASE_URL` の末尾の `/` の有無は問わない）にある公開鍵で ES256 / RS256 署名された有効なアクセストークンは、認証が通り、`sub` がユーザー ID、`email` がメールアドレスになる
- 追加: **AC-platform-03**: 署名が合わない、期限切れ、JWKS に無い鍵（`kid`）で署名された、ES256 / RS256 なのに `kid` が無い、`sub` が無い（anon / service_role のキーなど）、のどれかのトークンは 401
- 追加: **AC-platform-04**: 許可していない署名方式（`none`、HS512 など、HS256 / ES256 / RS256 以外）のトークンは 401
- 追加: **AC-platform-05**: `Authorization: Bearer` が無い・形式が違うときは 401（今までと同じ）
- 追加: **AC-platform-06**: JWKS の取得に失敗したとき、公開鍵方式のトークンは 401 になり、500 にはならない。HS256 のトークンは JWKS を取りに行かない
- 追加: **AC-platform-07**（非機能）: 取得した JWKS は isolate の中で 10 分使い回し、リクエストのたびには取りに行かない。JWKS に無い `kid` が来たときは取り直すが、取り直しは 30 秒に 1 回まで（不正なトークンで Supabase へ問い合わせが殺到しないように）
- 不変条件の追加: **INV-1**: 共有シークレットは HS256 のトークンの検証にだけ使い、公開鍵方式のトークンは JWKS の鍵でだけ検証する（署名方式の取り違えで検証を素通りさせない。ヘッダーの `alg` と、`kid` が指す鍵の種類が合わないトークンも通さない）
- 不変条件の追加: **INV-2**: Workers では、あるリクエストで始めた通信を別のリクエストから待たない。jose の `createRemoteJWKSet` は Workers の上では取得中の通信を共有しない作りなので、それを使う

## 実装計画

- **手本にする既存コード**:
  - `packages/api/src/lib/supabase.ts:7-21`（Workers の isolate の中で使い回すものを、モジュールの変数に遅延で持つ形）
  - `packages/api/src/middleware/auth.ts:34-47`（検証の失敗を `AppError(401, "Unauthorized", error)` にする形）
- **新しく作るファイル**:
  - `packages/api/src/lib/jwt.ts`: `verifySupabaseAccessToken(token, env)`。ヘッダーの `alg` が HS256 なら共有シークレット、ES256 / RS256 なら JWKS で検証して、ペイロードを返す。JWKS の URL を組み立てる小さな関数も置く。単体テストでは、JWKS の取得（グローバルの fetch）を差し替える
  - `packages/api/src/lib/jwt.test.ts`: 検証の単体テスト（AC-platform-01〜04、06、07、INV-1。INV-2 は Workers の上でしか起きないので、jose の実装の確認で代える）
  - `packages/api/src/middleware/auth.test.ts`: `jwtAuthMiddleware` を載せた小さな Hono アプリで、HTTP のステータスが 401 になることを確かめる単体テスト（AC-platform-03〜06。`onError` はテスト用に `AppError` のステータスを返すだけにし、DB に触れない）
- **変更するファイル**:
  - `packages/api/src/middleware/auth.ts`: `jwtVerify(token, secretKey)` を `verifySupabaseAccessToken(token, c.env)` に置き換える。ほかは変えない
- **設計の方針**:
  - jose の `jwtVerify` に「ヘッダーを見て鍵を返す関数」を渡し、`algorithms: ["HS256", "ES256", "RS256"]` で許可する方式を絞る。HS256 のときは共有シークレット、それ以外は `createRemoteJWKSet` の結果に任せる
  - `createRemoteJWKSet` の結果は、JWKS の URL ごとにモジュールの変数へ持ち、isolate の中で使い回す（手本の `lib/supabase.ts` と同じ形）。キャッシュの期間（10 分）と取り直しの間隔（30 秒）は jose の既定値で、AC-platform-07 を満たす
  - 今の検証に無い `iss` / `aud` の確認は、今回は足さない（挙動を変える範囲を認証方式の追加に絞る。「対象外」に書く）
- **代替案とトレードオフ**:
  - 推奨: 上の「両方式に対応」。本番は何も変わらず、ローカルと将来の本番に対応できる
  - 代替: テストだけ HS256 のトークンを自分で作る。API は変えずに済むが、ブラウザでログインする E2E がローカルで動かず、本番の鍵の切り替えにも備えられない（ユーザーが推奨案を選んだ）
  - 代替: `supabase.auth.getClaims()` に任せる。Supabase の推奨だが、HS256 のトークンでは Auth サーバーへの問い合わせになり、リクエストごとに通信が増える
- **確認したライブラリの使い方**:
  - jose 5.10.0（`packages/api/package.json` は `^5.3.0`）: `jwtVerify(token, getKey, { algorithms })` の `getKey` は `(protectedHeader, token) => key` を返せる。`createLocalJWKSet(jwks)` は JWKS の JSON から、ヘッダーの `kid` と `alg` に合う鍵を選ぶ（合う鍵が無ければ失敗する）。`createRemoteJWKSet` は、`cacheMaxAge` 600000（10 分）と `cooldownDuration` 30000（30 秒）が既定値。Cloudflare Workers の上で動いていると判定したときは、取得中の通信を共有せずに取り直す（`node_modules/.pnpm/jose@5.10.0/node_modules/jose/dist/browser/jwks/remote.js:79-82` で確認。spec-reviewer の指摘した Workers の I/O の制約への対応）
  - Supabase の JWKS は `<project>/auth/v1/.well-known/jwks.json`。共有シークレットは JWKS に載らない。Supabase の Edge でキャッシュされる（公式: https://supabase.com/docs/guides/auth/signing-keys）

## テスト方針

- **単体テスト**（`lib/jwt.test.ts`、DB 不要）: jose でテスト用の HS256 の秘密と ES256 / RS256 の鍵の組を作り、JWKS は `createLocalJWKSet` で差し替える
  - AC-platform-01 / 02: 有効なトークンが通り、`sub` と `email` が取れる
  - AC-platform-03: 改ざん、期限切れ、JWKS に無い `kid` が失敗する
  - AC-platform-04: `alg: none`、HS512 が失敗する
  - AC-platform-03: ES256 なのに `kid` が無い、`sub` が無い HS256 のトークン（anon のキーと同じ形）が失敗する
  - AC-platform-06: JWKS の取得に失敗すると検証が失敗する。HS256 では JWKS を取りに行かない
  - AC-platform-07: 2 回目の検証では取りに行かない。10 分たつと取り直す。知らない `kid` では取り直すが、30 秒以内の 2 回目は取りに行かない
  - INV-1: HS256 のヘッダーに公開鍵を、ES256 のヘッダーに共有シークレットを使わせようとしても通らない。`alg: RS256` で EC の鍵の `kid` を指すトークンも通らない
  - JWKS の URL: `SUPABASE_URL` の末尾に `/` があっても無くても同じ URL になる
- **ミドルウェアの単体テスト**（`middleware/auth.test.ts`）: 改ざん、期限切れ、`alg: none`、JWKS の取得の失敗、ヘッダーなしが、HTTP で 401 になる（500 にならない）
- **結合テスト**（ローカルの Supabase、`*.int.test.ts`）: 本物のログイン（ES256）で `fresh-user.int.test.ts` が通る（AC-platform-02）。テスト用ユーザーの `sub` と `email` を入れて、ローカルの `JWT_SECRET` で HS256 署名したトークンでも API が通る（AC-platform-01。今の本番と同じ方式）。認証なしは 401（AC-platform-05）
- **手動**: 人間が開発用の環境（ローカルの web と API。API は開発用の Supabase を向いている）でログインし、工数登録の画面が今までどおり動くことを確かめる（AC-platform-01 の念押し。開発用の Supabase は HS256）
