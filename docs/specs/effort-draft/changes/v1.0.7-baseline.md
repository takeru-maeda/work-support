### 要確認

1. **入力を手で全部消したとき、サーバーの下書きを残してよいか**: 今は、ブラウザの下書きだけを消し、サーバーには何も送らない。次に開くと、サーバーに残った前の内容が戻る。空のフォームを保存しない仕組み（`a8a5c14`）は、登録のあとの空のフォームが別の端末の下書きを空で上書きしないためのもの。推奨: 手で全部消したときはサーバーの下書きを `DELETE` する（登録のあとの空のフォームとは区別する）。P6 以降に改修の記録を通して直す
2. **サーバーに届いていないブラウザの下書きを、次に開いたときに消してよいか**: 最後の変更から 800 ミリ秒以内に画面を離れる（日常的に起きる）か、初めての保存に失敗したまま閉じると、サーバーは 204 を返し、「別の端末で登録済み」とみなしてブラウザの下書きを消す。入力が失われる。推奨: 画面を離れるときに待っている保存をすぐ送る（取り消さない）改修を P6 以降に行う。204 のときにブラウザの下書きを消す判定は、別の端末での登録のあとに古い下書きが復活しないために残す
3. **開いている画面どうしを同期しなくてよいか**: 古い画面で 1 文字でも編集すると、別の端末の新しい入力を上書きする。画面を開いただけでも時刻が新しくなる。推奨: 画面に戻ったとき（フォーカス）にサーバーの下書きの時刻を見て、新しければ知らせるか読み直す改修を P6 以降に検討する（入力中の内容との兼ね合いがあるので、仕様を決めてから）
4. **送信を待っている間の編集を許してよいか**: その間の保存が `DELETE` のあとに届くと、登録した内容が下書きとして復活しうる（ポストモーテムと同じ症状）。推奨: 送信中は入力欄を操作できないようにする（小さな改修として P6 で直す）
5. **サーバーの下書きで、未入力の実績を 0 にしてよいか**: 別の端末で続きを開くと 0 が入り、必須の入力のチェックを通ってしまう。推奨: 下書きでは未入力を未入力のまま保存する（スキーマの `hours` を下書きだけ null 可にする）。P6 以降に改修の記録を通して直す
6. **`updated_at` が更新されないのは意図どおりか**: 判定には使っていないので害は無いが、名前と中身が違う。推奨: 上書きのときに更新する（小さな修正として P6 で直す）

## 仕様レビュー（spec-reviewer）

- Major 8 件、Minor 5 件を受けて spec.md を直した。主なもの: メモは `entries` の JSON ではなく `memo` 列にある、`updated_at` は更新されない、800 ミリ秒以内に画面を離れると保存が送られず入力が失われる、開いている画面どうしは同期しない、送信を待っている間の編集は守られていない、サーバーの下書きでは未入力の実績が 0 になる。AC は、テストで判定できるように分岐ごとに分け（AC-08〜14）、今の不具合（仮の日付の選択）は AC から外して既知の落とし穴だけに置いた
- 事実の確認: 日付が `entries` 列の JSON の中に保存されて `GET` で戻ること、同じ時刻の `PUT` が捨てられること、`DELETE` のあとは古い時刻の `PUT` でも作り直すこと、`DELETE` は下書きが無くても 204 であることを、ローカルの Supabase で動かして確かめた

## 対象外

- コードの修正（P5 ではコードを変えない。直すものは計画書の P6 に足す）
- 工数登録画面そのもの（入力の部品、undo / redo、完了メール）は effort-entry の仕様
