# 工数登録の下書き（端末間の同期と競合の制御）

## TL;DR・改修前の必読

- 工数登録画面（`/efforts/new`）の入力途中の内容を、ブラウザ（localStorage）とサーバー（`work_entry_drafts`、ユーザーごとに 1 件）の両方に自動で保存し、別の端末やリロードのあとでも続きから入力できるようにする
- 競合は「クライアントの保存の時刻（`clientUpdatedAt`）が新しいほうを残す」で決める。開いている画面どうしは同期しない（開いたときに 1 回だけ読む）
- ⚠️ 改修の前に [§設計不変条件](#設計不変条件) と [§ポストモーテム](#ポストモーテム) を読む。登録（送信）と下書きの保存の順番を崩すと、登録済みの内容が下書きとして復活する（2026-01 に実際に起きた）
- ⚠️ 入力が失われる・古い内容に戻る経路が、ほかにもいくつか残っている（[§既知の落とし穴](#既知の落とし穴)）

## 目的と利用者

- 目的: 工数の入力を途中でやめても、別の端末やあとで続きから入力できるようにする。入力が失われないようにする
- 利用者と使う場面: PC で入力を始めてスマートフォンで続ける、タブを閉じてあとで戻る、など

## 振る舞いと受け入れ基準

### API（`/api/effort/draft`、JWT）

- **AC-effort-draft-01**: `GET` は、そのユーザーの下書きがあれば `200 { draft: { entries, memo, date, updated_at, client_updated_at } }`、無ければ `204`
- **AC-effort-draft-02**: `PUT` は、下書きが無ければ、`clientUpdatedAt` の新旧に関わらず作る。あれば、受け取った `clientUpdatedAt` が保存済みの `client_updated_at` より**新しいときだけ**上書きする。保存したら `200 { applied: true, draft: { user_id, date, updated_at } }`、同じか古ければ保存せず `200 { applied: false, reason: "Stale clientUpdatedAt" }`
- **AC-effort-draft-03**: `PUT` の本文は `{ date: "YYYY-MM-DD" | null, entries: [...], memo?: string | null, clientUpdatedAt: <タイムゾーン付きの ISO 8601> }`。形が違えば 400（タイムゾーンの無い `clientUpdatedAt` も 400）
- **AC-effort-draft-04**: `DELETE` は、そのユーザーの下書きを消して `204`。下書きが無くても `204`
- **AC-effort-draft-05**: どの操作も、トークンのユーザーの下書きだけを読み書きする。下書きはユーザーごとに 1 件。トークンが無ければ 401

### 画面（工数登録画面の下書きの扱い）

- **AC-effort-draft-06**: フォームの内容（日付、案件・タスク・工数、メモ）が変わるたびに（undo / redo、並べ替え、画面を開いて復元した直後を含む）、ブラウザ（localStorage のキー `effort:entry:form_<ユーザー ID>`）にすぐ保存する。サーバーには、最後の変更から 800 ミリ秒たったら 1 回だけ `PUT` する（800 ミリ秒以内に次の変更があれば待ち直す）。`clientUpdatedAt` は、その保存の処理が動いた時刻
- **AC-effort-draft-07**: エントリーが 0 件で、メモが空か空白だけで、日付が未選択（3 つすべてを満たす）のときは、サーバーに保存せず、ブラウザの下書きを消す。日付だけを選んだ状態は保存する
- **AC-effort-draft-08**: 画面を開いたら、サーバーの下書きの取得が終わるまで、エントリーと集計とメモの欄の代わりに読み込み中の表示を出し、送信のボタンは押せない
- **AC-effort-draft-09**: 取得が終わったら、サーバーとブラウザの両方に下書きがあれば、`clientUpdatedAt` が新しいほうを初期の内容にする（同じならサーバー。片方の時刻が無ければ時刻のあるほう。両方に無ければサーバー）。サーバーにだけあれば、サーバーの下書き
- **AC-effort-draft-10**: ブラウザにだけ下書きがあり、サーバーが「下書きなし」（204）を返したときは、別の端末で登録が済んだとみなし、ブラウザの下書きを消して空から始める
- **AC-effort-draft-11**: サーバーの下書きの取得に失敗したときは「下書きの取得に失敗しました」のトーストを出し、ブラウザの下書きがあればそれを初期の内容にする。ブラウザの下書きが壊れた JSON なら、黙って消して `error_logs` に送る
- **AC-effort-draft-12**: 登録が成功したら、それより前に始まっていたサーバーへの保存を送らず、`DELETE /api/effort/draft` を 1 回送り、フォームを空に戻して undo の履歴を消し、ブラウザの下書きを消す。空に戻したあとに `PUT` は送らない。サーバーの下書きの削除に失敗しても、利用者には知らせない（`error_logs` に送る）
- **AC-effort-draft-13**: 登録に失敗したときは「工数の送信に失敗しました。」を出し、入力とブラウザの下書きは残る。サーバーの下書きは、送信の直前の変更を含まない（次に編集すると保存し直す）
- **AC-effort-draft-14**: サーバーへの保存に失敗したときは「ドラフトの保存に失敗しました。」を出す。`applied: false`（古いとして捨てられた）のときは何も出さない

## 画面と API

### 画面
- ルート: `/efforts/new`（工数登録画面。画面全体は effort-entry の仕様）
- この機能が持つのは、入力の自動保存、初期の内容の復元、送信のあとの下書きの削除

### API
| メソッドとパス | 認証 | 入力 | 出力 | 主なエラー |
| --- | --- | --- | --- | --- |
| `GET /api/effort/draft` | JWT | なし | `EffortDraftResponseSchema`（または 204） | 401 |
| `PUT /api/effort/draft` | JWT | `EffortDraftSchema` | `EffortDraftUpsertResponseSchema` | 400、401、500 |
| `DELETE /api/effort/draft` | JWT | なし | 204 | 401 |

スキーマは `packages/shared/src/schemas/effort.ts`。全エンドポイントは [docs/reference/api.md](../../reference/api.md)。

## データ

- [work_entry_drafts](../../reference/database.md#work_entry_drafts): ユーザーごとに 1 行（`user_id` は一意）。`client_updated_at` で競合を判定する
  - **`entries` 列の JSON は `{ date, entries }`**（日付はここに入る。`date` の列は無い）。メモは `memo` 列
  - `updated_at` は**最初に作った時刻のまま**で、上書きしても変わらない（既定値 `now()` だけで、更新でもトリガーでも変えていない）。判定には使わない
- サーバーには API の形（`project_id`、`hours` など）で保存する。**未入力の実績は 0 にして送る**。行の ID やグループの ID は保存せず、復元のたびに作り直す
- ブラウザ: localStorage の `effort:entry:form_<ユーザー ID>`（`{ date, memo, entries, clientUpdatedAt }`）。フォームの形のまま保存するので、未入力の実績は未入力のまま

## 設計不変条件

- **INV-1**: サーバーは、下書きがあるときは、受け取った `clientUpdatedAt` が保存済みより**新しいときだけ**上書きする（同じなら捨てる）。破ると、遅れて届いた古い保存が新しい入力を上書きし、入力が古い内容に戻る
- **INV-2**: 登録の成功のあと、登録した内容の下書きの保存がサーバーに届いてはいけない。送信の最初に待っている保存を取り消し、フォームを空に戻す前に次の 1 回の保存を飛ばす設定にし、undo の履歴を消す。**サーバーは、下書きを消したあとの保存を古い時刻でも受け付けて作り直す**ので、守りは web の側にしかない。破ると、登録した内容が下書きとして復活し、気づかずに 2 回登録する（[§ポストモーテム](#ポストモーテム)）。ただし、送信を待っている間の編集は守られていない（[§既知の落とし穴](#既知の落とし穴)）
- **INV-3**: 空のフォームはサーバーに保存しない。破ると、登録のあとの空のフォームが保存され、別の端末の入力途中の下書きを空で上書きする
- **INV-4**: 下書きはトークンのユーザーの ID でだけ読み書きする（API は `user_id` の条件、ブラウザはユーザーごとのキー）。破ると、別のユーザーの入力途中の内容が見える

## エラー時の挙動

- サーバーの下書きの取得に失敗: トースト「下書きの取得に失敗しました」。画面を開いたときだけでなく、保存のあとの読み直しに失敗したときも、編集の途中で出る
- サーバーへの保存に失敗: トースト「ドラフトの保存に失敗しました。」。通信の失敗のほか、送る前や受け取ったあとの形の検証に失敗したときも出る。ブラウザには保存済み
- 登録のあとのサーバーの下書きの削除に失敗: 利用者には知らせない。サーバーに登録済みの内容の下書きが残るので、次に開くと（ブラウザの下書きは消してあるため）その内容が戻る
- API のエラー: 401 と 500 は `{ error, accessLogId }`（platform）。`PUT` の本文の形の誤りの 400 は、検証ライブラリの既定の形（`{ data, error: [...], success: false }`）

## 既知の落とし穴

- **読み込み中の日付の選択は仮のもの**: サーバーの下書きの取得が終わるまで、日付の欄に、開けるが選んでも反映されない日付の選択を出している（`EffortForm` の `isInitializing` の間の `<DatePicker />`）。開いてすぐ日付を選ぶと入らない。通信が遅いと利用者にも起きる。P6 で直す予定。E2E（`packages/e2e/tests/effort.spec.ts`）は、下書きの取得を待ってから操作している
- **最後の変更から 800 ミリ秒以内に画面を離れると、サーバーへの保存は送られない**（離れるときにすぐ送る形に直す予定。P6。画面を閉じるときに待っている保存を取り消すため）。サーバーに下書きがまだ無いときにこれが起きると、次に開いたときに AC-10 の経路に入り、ブラウザの下書きも消えて入力が失われる。初めてのサーバーへの保存に失敗したまま閉じたときも同じ
- **開いている画面どうしは同期しない**（P6 以降に仕様を決めてから直す予定）: 初期の内容は開いたときに 1 回だけ決める。端末 B で古い画面を開いたまま、端末 A で入力し、そのあと B で 1 文字でも編集すると、B の古い内容が新しい時刻で保存され、A の入力を上書きする（INV-1 では防げない）
- **画面を開いただけで、下書きの時刻が新しくなる**（AC-06。復元した内容を今の時刻で保存し直す）。古い内容の画面を開いただけで、ほかの端末の下書きより新しいとみなされる
- **送信を待っている間の編集は守られていない**（送信中は入力を止める形に直す予定。P6）: 送信のボタンを押したあとも入力欄は操作できる。その間の編集で始まったサーバーへの保存が、`DELETE` のあとに届くと下書きが作り直される（登録の API が 800 ミリ秒より長くかかったとき）。成功したあとは、その編集もフォームを空に戻すときに消える
- **入力を手で全部消しても、サーバーの下書きは消えない**（AC-07 はブラウザの下書きを消すだけ。サーバーの下書きも消す形に直す予定。P6）。次に開くと、サーバーに残った前の内容が戻る
- **別の端末で続きを開くと、未入力だった実績が 0 になる**（データ）。必須の入力のチェックも通ってしまう（下書きでは未入力のまま保存する形に直す予定。P6）
- **競合の判定は各端末の時計に頼る**。端末の時計がずれていると、新しい入力が古いとみなされて捨てられる
- **サーバーの判定は「読んでから書く」で、まとめて行っていない**。同じユーザーの保存がほぼ同時に 2 つ届くと、下書きがあるときは古いほうが残ることがあり、無いときは 2 つ目が一意の制約に当たって 500（「ドラフトの保存に失敗しました。」）になる
- 日付は `date` の列ではなく `entries` 列の JSON の中にあり、`updated_at` は更新されない（DB を直接見るときの注意）

## ポストモーテム

### 2026-01-23 症状「工数を登録したのに、次に開くと登録した内容が下書きとして戻ってくる」「空の下書きが保存される」（v1.0.7）
- **真因**: 入力の変更から 800 ミリ秒後にサーバーへ保存するタイマーが、送信の処理の間も残っていた。空に戻すときの保存を 1 回飛ばす仕組み（`skipNextDraftSync`）はあったが、送信より前に始まっていたタイマーは止めていなかった。登録が成功して下書きを `DELETE` したあとで、そのタイマーが登録した内容を `PUT` し、サーバーは（下書きが無いので）新しい下書きとして作り直した。また、空のフォームも保存していた
- **対策**: 送信の最初に待っている保存を取り消す（`cancelSync` を追加）、空のフォームは保存しない（ガードを追加）（INV-2、INV-3）
- **再発時に確認すること**: 送信の処理の中で、`cancelSync` が `submitEffortEntries` より前に呼ばれているか。フォームを空に戻す前に `skipNextDraftSync` が呼ばれているか。下書きの保存のタイマーや遅延の長さを変えていないか。送信を待っている間の編集で新しいタイマーが始まっていないか（既知の落とし穴）。サーバーは消したあとの保存を受け付けるので、web 以外の守りは無い
- **改修の記録**: 移行前のため無し（コミット `a8a5c14`）
