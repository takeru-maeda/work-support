# バックログ

ハーネスの移行（[harness-migration.md](active/harness-migration.md)）の P5 で見つけ、P6 で直す予定だった不具合と改善。新規開発を優先するため、2026-10-15 に移行計画から外してここへ移した（ユーザーの判断）。

- どれも、今の振る舞いを各機能の `spec.md` の「既知の落とし穴」とテストで固めてある。直すときは、そのテストを先に Red に書き換える（`docs/steering/testing.md`）
- 仕様書やコードに残る「P6 で直す予定」「`TODO(P6)`」「未（P6）」の印は、このバックログを指す
- 新規開発でその機能に触れるときに、関係する項目を一緒に直すのを基本とする。直すときは、それぞれ改修の記録を通す。直したら、その項目を消す
- GAS（Google Form）からの取り込みは今は使っていないので、その項目は使い始めるときまで後回しにする

## 直すもの

- effort-ingest-gas（GAS からの取り込み。使い始めるときまで後回し）: 1 回の送信を、全部保存するか全部保存しないかにする（途中で失敗すると一部だけ残り、送り直すと 2 重になるため）。effort-entry の「送信をまとめて保存する」と合わせて設計する。本番に出す前に、Google Form の説明文に書式を書く（v1.1.2 で書き間違いを 400 にしたため。`docs/plans/active/release-v1.1.md`）
- P4 の E2E で見つけた不具合: 工数登録の画面を開いてすぐ（下書きの `GET /api/effort/draft` が返る前に）日付を選ぶと、入らない。読み込み中は、開けるが選んでも反映されない仮の日付の選択を出しているため（`EffortForm` の `isInitializing` の間の `<DatePicker />`。P5 で仕組みを確かめて記述を直した）。通信が遅いと利用者にも起きる。改修の記録を通して直す（読み込み中は操作できない表示にする、など）。直したら `packages/e2e/tests/effort.spec.ts` の待ち合わせ（`TODO(P6)`）を外す
- P5 で決めた effort-draft の直し（`docs/specs/effort-draft/changes/v1.0.7-baseline.md` の「人間の判断」。それぞれ改修の記録を通す）
  - 手で全部消したときは、サーバーの下書きも消す（登録のあとの空のフォームとは区別する）
  - 画面を離れるときは、待っている保存を取り消さずにすぐ送る（最後の変更から 800 ミリ秒以内に離れると入力が失われるため）
  - 開いている画面どうしの同期（古いタブでの編集が別の端末の新しい入力を上書きする）は、仕様を決めてから直す
  - 送信を待っている間は入力を止める（登録した内容が下書きとして復活しうるため）
  - 下書きでは未入力の実績を未入力のまま保存する（別の端末で開くと 0 になるため）
  - 下書きの上書きのときに `updated_at` を更新する
- P5 で決めた goals の直し（`docs/specs/goals/changes/v1.0.7-baseline.md` の「人間の判断」。それぞれ改修の記録を通す）
  - 週の境目を日本時間の月曜 0:00 にする（前週からの差分と週報を同じ改修でそろえる）
  - 履歴の無い目標の前週の値を 0 にする（週報とそろえる）
  - 期間の追加を、1 つの期間の目標をまとめて作る API にし、サーバーで期間の前後・重なり・重みの合計を確かめて、全部作るか何も作らないかにする。`PUT` は期間を受け付けない
  - 前週の進捗の履歴を件数の上限なしで取っている（`max_rows` を超えると今の目標の履歴が切り捨てられ、差分が黙って +0.0% になる）。目標ごとに最新の 1 件だけ取る
  - 追加の画面で、目標名が空の行が保存の時に黙って外される
  - 表の「更新」の途中で失敗すると、まだ保存していない編集が消える（1 件ごとの成功で一覧を取り直すため）。内容のダイアログの保存や削除でも、表の編集中の値が消える
  - 内容のダイアログが失敗しても閉じて入力が失われる。保存中も押せる
  - 過去の目標の検索: キーワードの `,` で 500、最後のページより先で 500、エラーのトーストが描画のたびに出続ける（壊れた条件は保存され、開くたびに続く）、並び順に同じ値があるとページをまたいで重複・抜けが出る
  - `:id` が数字でないと 500、本文が空の `PUT` が 400 `Goal not found`
  - `PUT` で `updated_at` を更新する
- P5 で決めた weekly-report の直し（`docs/specs/weekly-report/changes/v1.0.7-baseline.md` の「人間の判断」。それぞれ改修の記録を通す。週の境目を日本時間にする直しは goals と同じ改修で行う）
  - 土日に工数がある日は日別の行にも出し、平均の分母にも数える
  - 日別の時間を丸めずに出している（`3.3000000000000003h` になる）
  - 週の計算が実行環境のタイムゾーンに依存する（日本時間で動かすと日曜〜土曜にずれる）
  - 進捗の履歴を件数の上限なしで取っている（`max_rows` を超えると週の始まりの値が 0 になる）。履歴のクエリを `user_id` でも絞る
  - 重みが同じ目標の並びと、期待値に使う目標が決まらない（DB の返す順）
  - 画面: 日付を変えても前の週の本文が残る、コピーの失敗を知らせない、エラーの文を英語のまま出す
- P5 で決めた missions の直し（`docs/specs/missions/changes/v1.0.7-baseline.md` の「人間の判断」。それぞれ改修の記録を通す）
  - 保存中は「キャンセル」と入力を止める（保存中にキャンセルして保存が失敗すると入力が戻らない、保存中に打ち足した文字が捨てられるため）
  - 編集中に取り直しが失敗しても、入力欄を隠さない
  - まだミッションが無いユーザーが同時に 2 回保存すると片方が 500 になる（1 回の upsert にする）
  - 取得に失敗したときのエラーの文を、英語のまま出さない
- P5 で決めた effort-entry の直し（`docs/specs/effort-entry/changes/v1.0.7-baseline.md` の「人間の判断」。それぞれ改修の記録を通す）
  - 送信をまとめて保存する（全部保存するか全部保存しないか。effort-ingest-gas の直しと合わせて設計する）。候補の一覧の作り直しの失敗は、保存の成功として返す
  - キーボードの undo / redo を、確認のダイアログを開いている間と送信中は効かないようにする
  - 100 時間以上で DB の桁あふれの 500 になる（スキーマで 100 未満にして 400 にし、画面でも止める）。負の値を画面で止める
  - 大文字小文字の扱いを「区別する」にそろえる（送信の中の使い回し、画面のタスクの候補、集計のまとまり）。「案件A」があるところで「案件a」と打ってタスクを選ぶと 400 になり案件だけが残る件も、これで解消する
  - 同じ送信の中で、使い回したタスクの ID が案件を確かめない
  - 完了メールの失敗を `error_logs` に残す。GAS が JSON 以外を返したときも扱う。【集計】の前の空行を 1 行にする
  - 同じ案件・タスクを画面で 2 つ入れられる（名前の打ち込みで候補の除外をすり抜ける）
  - 案件名を打っている途中で、既存の案件名と一致した瞬間に候補の一覧が閉じる
  - 開発用サーバーで undo の 1 歩が 2 回ずつ記録される（履歴の記録を状態の更新の外に出す）
  - 案件を変えたときに、2 つ目以降のタスクの「必須入力」が消えないことがある（直すときに確かめる）
- P5 で決めた effort-list の直し（`docs/specs/effort-list/changes/v1.0.7-baseline.md` の「人間の判断」。それぞれ改修の記録を通す）
  - 集計を、絞り込んだ全体の合計にする（API で合計を返し、画面はそれを出す）
  - 並べ替えの同じ値の行の順番が決まらず、ページ送りで重複・抜けが起きうる（最後に ID で並べる）
  - 最後のページより先で 500（goals の過去の目標の検索と同じ直し方にする）
  - 絞り込みで案件を変えても、前に選んだタスクが残って 0 件になる
  - 保存した条件を確かめない（件数が壊れていると失敗が続く、日付が壊れていると画面全体が落ちる）
  - 読み込み中も集計だけ前の条件の数字が出る。最初の取得に失敗すると「工数データがまだ登録されていません」が出る
  - 集計の小数の誤差（「-0.00h」「0.30h」）。表と集計で小数の桁が違う
- P5 で決めた残りの機能の直し（各機能の `docs/specs/<feature>/changes/v1.0.7-baseline.md` の「人間の判断」と「見つけた不具合」。それぞれ改修の記録を通す）
  - auth: ログイン済みなら `/login`・`/signup`・`/landing` と存在しないパスをホームへ。ヘッダーのログアウトをこの端末だけにする。別のタブでアカウントが替わると別人のデータが混ざる（`onAuthStateChange` で受けてストアと SWR を消す）。通信の失敗で未ログイン扱い。画面を移るたびの確かめ直し。ローカルの再設定のリンクの戻り先。ほか
  - platform: 本番では OpenAPI と Swagger UI を出さない。DB のエラーの文を応答に出さない。壊れた JSON を 400 にする。アクセスログが書けないと全部止まる。開発用の Origin が本番で許可される。エラーの記録の API の上限。`reportUiError` が失敗を投げる。ほか
  - profile: アカウントの削除の途中の失敗で 500 になりログインのまま残る、2 回目の削除が 500。削除のたびのアクセスログの更新の失敗。削除のあとにストアと端末のデータを消さない。画像の保存の失敗で前の画像が消える。名前が空のユーザーにメールアドレスが保存される。ほか
  - user-settings: 作成の同時送信で 500。最初の 404 が ERROR として残る。初期化の失敗で前の値が残る。ログアウトで設定のストアを消さない。テーマのちらつき。ほか
  - app-shell: 画面全体のエラーの受け止め（真っ白になる）。下の階層でナビが選ばれない。ホームとプロフィールの器。本文の最後がナビに隠れうる。拡大の停止。ほか
  - landing: 「Google連携に対応」の文言を消す。影と模様が描かれない。リンクの中のボタン。よくある質問のアクセシビリティ。ほか
- P4 で見つけた潜在的な不具合: 目標の履歴の検索で `minProgress` / `maxProgress` に空文字か null を渡すと、「指定なし」にならず 400 になる（`GoalHistoryQuerySchema` の前処理のあとで `z.coerce.number()` が NaN にする）。web は値があるときだけ送るので画面からは起きない。`packages/shared/src/schemas/goals.test.ts` の `it.fails` を `it` に戻す形で、改修の記録を通して直す
- P2 で保留にしたフックの依存配列の 2 件を、テストを書いてから改修の記録を通して直す（コードに `TODO(P6)` の印）
  - `useEffortSummaryMetrics`: `projectOptions` の読み込みが終わっても案件名が更新されない可能性
  - `useEffortSubmission`: `cancelSync`（`useEffortDraftSync` で毎回作り直される）が依存に無い
- 主要な画面の E2E シナリオ
